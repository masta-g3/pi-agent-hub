Read a row as separate facts

  • Runtime status (⠋ ◐ ○ × -): is Pi working, done, or gone? Comes from tmux plus the heartbeat.
  • Request (? ✓ !): a Pi extension asked for you. Comes from the extension, through the heartbeat.
  • Workflow position (✓ ◉ ·): where the workflow says it is. Comes from the workflow extension.
  • Section: Hub sorts each tree into NEEDS YOU, HEALTH, ACTIVE, or QUIET from the facts above.
  • Your labels: group and Backlog/Archive. You set them; Hub stores them.

One fact never changes another. A waiting icon is not a request, and a checked step does not mean the agent is idle.

From Pi to your row: two inputs, read every second

Hub does not watch your terminal output. It reads two things: whether the tmux session exists, and a small JSON file that a Pi extension rewrites. Once a second, the dashboard combines both into a row.

running code file on disk, under the Hub state folder tmux session tmux presence check
60 s

A heartbeat older than this is stale. Hub stops trusting its state and uses the last state it knew.

Saved vs. memory

Status, your read time, labels and the last workflow position go to registry.json. Requests and ticket context stay in memory and come only from a fresh heartbeat.

Safe to be wrong

Hub checks each optional part of the heartbeat on its own. A malformed workflow entry is dropped; the liveness part still counts.

The status icon: the first matching rule wins

The status icon answers one question: what is the Pi process doing right now? Hub checks these rules in order on every refresh and stops at the first match. The rule list follows computeStatus() in src/core/status.ts.

  1. No tmux session, and Hub stopped it on purposeyou stopped it, or a lifecycle action did-stopped
  2. No tmux session, or tmux did not answerthe process died or tmux failed×error
  3. No heartbeat file yetuse the fallback belowfallback
  4. Heartbeat says errorfor example, Fork and compact failed×error
  5. Heartbeat says shutdownPi exited cleanly-stopped
  6. Heartbeat is older than 60 suse the fallback belowfallback
  7. Heartbeat says running or starting⠋running
  8. Agent finished after you last opened the session◐waiting
  9. You opened the session after the agent finished○idle

Fallback: Hub cannot see live work without a fresh heartbeat. A starting session stays starting. Any other session shows ◐ waiting, or ○ idle if you have opened it before.

Waiting is not a request

A session that finished its turn shows ◐ waiting. That does not mean it needs you. Only a Pi extension can ask for you, by publishing a request with a kind and a short text. Hub shows that request only on waiting or idle rows.

How Hub picks a section

Hub sorts each whole tree (a parent and its children) by checking the parent first. The first match wins.

  1. NEEDS YOUThe parent is waiting or idle and has a request you have not read.
  2. HEALTHThe parent shows × error.
  3. ACTIVEThe parent or any child is starting or running. In the frame above, “Dashboard UI polish” is ◐ waiting but sits in ACTIVE because its child is ⠋ running.
  4. QUIETEverything else that is not archived.
  5. ARCHIVEDYour Archive choice puts the tree here, newest first. Archiving does not stop Pi.

Rules you can rely on

  • A child never changes its parent. A child's request shows as ?1 on the parent and ?1 child on the section. A child's error stays on the child.
  • Opening marks it read. Enter, a pin focus, or a records your read time. The request disappears until the extension publishes a newer one.
  • Looking does not mark it read. Creating a pin, searching, or opening details changes nothing.
  • New requests announce once. A new request with an ID can show a six-second band, and a tmux message when you are elsewhere. Requests that existed when Hub started stay silent.
  • Inside a session you still see the count. The tmux bar shows ⚑ N need you · alt+w next. Alt+W opens the next one.
  • Bell and desktop alerts are off by default. Turn on the bell with Attention bell in :. Turn on desktop alerts with dashboard.attentionNotify.

The workflow rail shows position, not proof

The step columns come from the workflow extension, not from Hub. Rules supplies Plan, Execute, Review, Reflect and Commit; another extension can supply other steps. The extension reports the current step and, optionally, whether that step is complete. Hub draws the markers from position alone.

  • Kept after stop. Hub saves the last position in registry.json, so a stopped row still shows where it ended.
  • Modes do not move columns. A mode such as Rules' focus mode (FOC) shows in the row details only.
  • Read-only. The board (S) groups Active trees by step. It never starts a step or marks one complete.

When you doubt a row, ask for the evidence

Press i on a selected session, or run pi-hub explain <id-or-prefix>. Hub shows the inputs that produced the icon and the section. The command only reads; it does not update the registry.

What Hub never reads to decide a row:

  • your terminal output or pane text;
  • your Pi conversation;
  • guesses about idle time or workflow progress.

Read each mark on a row as a separate claim. The icon comes from tmux and the heartbeat. Requests and steps come from Pi extensions. Sections and labels come from Hub. If a claim looks wrong, i shows its source.
