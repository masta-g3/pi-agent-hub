# pi-agent-hub Structure

`pi-agent-hub` is a minimal TypeScript package for managing Pi coding-agent sessions in tmux. It is Pi-only: Pi remains the agent runtime, tmux remains the process substrate, and this package supplies the dashboard/registry glue.

## Layout

```text
src/
  cli.ts                 command entrypoint (`pi-hub`; `pi-agent-hub` remains an alias)
  index.ts               public exports
  app/                   dashboard launcher, controller, refresh loop, and shared session actions for the standalone TUI
  core/                  shared heartbeat intake, JSON store/locking, registry, paths, tmux, Pi process args, status reducer, multi-repo workspace and worktree helpers
  extension/             tiny Pi extension for session heartbeats
  mcp/                   MCP catalog/project config, direct clients, pool, tool adapter
  skills/                project skill attach/detach and pool discovery
  tui/                   pure render model, terminal layout, dialog modules, shared text/form primitives, picker, and theme helpers
test/                    Node test-runner tests compiled by TypeScript
package.json             npm package metadata, SemVer version, CLI bins, and Pi extension declaration
CHANGELOG.md             npm/GitHub release notes, maintained per published version
docs/STRUCTURE.md        this developer onboarding guide
docs/FEATURES.md         user-facing feature map and dashboard workflow
docs/CONFIG.md           runtime state, global config, themes, Skills/MCP setup
docs/DEVELOPMENT.md      local setup, tests, package checks, smoke testing, release workflow
docs/history/             archived feature notes; useful context, not current product contracts
```

## Runtime state

- Global state lives under `PI_AGENT_HUB_DIR` or `<PI_CODING_AGENT_DIR>/pi-agent-hub`.
- Optional global config lives at `config.json`; it can set skill pool directories, the MCP catalog path, a managed-session `session.prelude` shell snippet, and `session.worktreeDefault` for new-session forms.
- The session registry is `registry.json`; the dashboard's independent grouping/density selection is persisted in `ui-state.json` beside it. Density accepts `compact` or `all-cards`. `collapsedSections` still accepts `backlog` and `archived`, but only Archived is a collapsible section in the project cockpit; a persisted Backlog value is inert. Missing, malformed, or unknown values are ignored; view state falls back to the project cockpit, compact rows, and expanded Archived.
- `pi-hub` opens a stable dashboard tmux session named `pi-agent-hub`; use `pi-hub tui` to run the TUI directly without the dashboard wrapper. The `pi-agent-hub` command remains available as a compatibility alias.
- Managed Pi sessions write heartbeat files under `heartbeats/<session-id>.json` through the extension. `src/core/heartbeat.ts` reads each file as unknown data, requires a valid liveness envelope and a `managedSessionId` matching the requested file, then normalizes optional identity, theme, context, and workflow data before dashboard use. A malformed envelope is treated as a missing heartbeat; malformed optional metadata is omitted without hiding valid liveness. Unknown producer fields remain compatible. Each valid heartbeat can include Pi's native session name, the latest valid producer-neutral `pi-agent-hub-context` snapshot, and optional producer-owned workflow runtime. The registry title starts as the primary repo basename and becomes a cache of nonblank heartbeat names. Generic subtitle, description, and attention remain runtime-only. Workflow activity and deterministic plan progress travel inside `workflow-runtime`; Hub does not read producer files or a metadata sidecar.
- Optional `pi-tmux-subagents` compatibility uses flat registry rows with `kind: "subagent"`, `parentId`, `agentName`, `taskPreview`, and `resultPath`; the dashboard renders those rows nested under their parent with a short agent-name row label, while task preview belongs in the action workspace and filtering. Standalone subagent state remains owned by `pi-tmux-subagents`, and dashboard refresh prunes subagent rows whose tmux sessions are gone so stale completed rows do not linger.
- Managed tmux sessions use the `pi-agent-hub-<first-12-session-id-chars>` name. If `session.prelude` is configured, it runs inside the managed tmux shell before `exec pi`; dashboard launch and direct `pi-hub tui` do not run it.
- Multi-repo sessions keep `ManagedSession.cwd` as the primary repo and start Pi from `<global-state>/workspaces/<session-id>`, a symlink workspace containing the primary repo, each additional repo, and `.pi -> <primary>/.pi`. Every managed parent launch, including the direct normal-session fork path, exports `PI_AGENT_HUB_PRIMARY_CWD=ManagedSession.cwd`; it never exports `workspaceCwd` or an additional repo through that variable. This gives producer extensions one optional process-local project root when resumed conversation history retains a different Pi header cwd, without persisting the path or changing normal `f`/worktree behavior. If selected repo roots contain `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, or `CLAUDE.MD`, Hub generates a workspace-root `AGENTS.md` that labels and embeds those repo instructions so Pi loads them from the workspace cwd.
- Hub-owned worktree sessions keep `ManagedSession.cwd` as the primary worktree path and store metadata in the registry. New rows use `worktrees[]` with one entry per repo (`path`, source `repoRoot`, branch, base branch, role), while scalar `worktreePath`/repo/branch fields remain compatibility metadata. Worktrees live under `<global-state>/worktrees/<repo-name>/<session-id-prefix>-<branch-slug>`. At process start, `src/core/worktree-context.ts` validates the complete mapping and supplies one bounded guidance string to the Hub extension and the optional `pi-tmux-subagents` prompt bridge. The extension appends that guidance to each parent turn through `before_agent_start`; child launchers receive the same text through their package-owned boundary instead of loading Hub state.
- Recent repo choices for the new-session picker live in `<global-state>/repo-history.json`; current registry paths are merged with this bounded history at TUI startup.
- Project skill state lives in `<project>/.pi/sessions/skills.json`; available skills come from `skills.poolDirs` in global config or `<global-state>/skills/pool`.
- Project MCP enablement lives in `<project>/.pi/sessions/mcp.json`; available MCP servers come from the configured catalog path or `<global-state>/mcp.json`.
- JSON state files use `src/core/atomic-json.ts` for atomic writes, optional version/shape parsing, shared errno checks, and lock-dir guarded read-modify-write updates. `src/core/registry.ts` owns registry freshness: `loadRegistry()` reads state, while `updateRegistry()` is the sole registry write path. Registry updates compare their persisted JSON snapshot inside the lock and skip the atomic write when it is unchanged; other JSON stores retain their configured write behavior.
- In the standalone TUI, `<project>` for Skills/MCP pickers is the selected session's primary cwd, with dashboard cwd as the fallback when nothing is selected. For multi-repo sessions, Skills/MCP state applies to the primary repo only.
- Pooled MCP uses a Unix socket at `<global-state>/pool/pool.sock`; run `pi-hub mcp-pool` explicitly when pooled servers are enabled.
- Inside-tmux switch return state lives under `return-key/` while a temporary `Ctrl+Q` binding is active; `pi-hub doctor` reports active/stale return state.

## Design rules

- Keep public names centralized in `src/core/names.ts`; `pi-hub` is the primary CLI command, `pi-agent-hub` is a compatibility alias, and runtime state/tmux names remain `pi-agent-hub`. CLI install diagnostics live in `src/core/install-diagnostics.ts`: they may warn and report exact PATH fixes, but must not mutate PATH, shell profiles, npm globals, or Pi package directories.
- Keep heartbeat shape and identity checks centralized in `src/core/heartbeat.ts`. Producer `workflow-runtime` entries identify position with `activeStep`, while persisted heartbeat workflows use `activeIndex`; separate adapters share step and decoration checks and must not accept the other position shape. The extension owns publication timing and atomic serialized writes. Keep liveness reduction and retention centralized in `src/core/status.ts`, and keep registry/runtime projection in `src/app/controller.ts`; neither layer reparses heartbeat metadata. The TUI acknowledges a `waiting` session before attach/switch so opening it clears the unread/waiting indicator; keep that ordering when changing attach behavior. Fresh managed-session heartbeats can also carry the active Pi theme snapshot used by that session's managed tmux chrome; stale or shutdown heartbeats must clear it so disk settings remain the per-session fallback. Dashboard theming is independent: synchronized mode reads Pi's global theme setting, detached mode reads Hub's override, and neither follows a heartbeat/session anchor. The heartbeat `workflow` snapshot (bridged from the optional workflow-runtime extension; see CONFIG.md) is the deliberate contrast: it is state about the work, not live chrome, so `applyComputedStatus` adopts it from fresh heartbeats but retains the last known value across stale/shutdown heartbeats — a stopped-but-Active session remains eligible for its board lane. The latest heartbeat `stateSince` is retained as `lastActivityAt`; compaction heartbeats use the pre-compaction `stateSince` so transient green compaction activity does not make an old session newly recent. `workflow.updatedAt` is the producer's state-change timestamp and may advance within one step, while heartbeat `updatedAt` remains the independent liveness timestamp.
- Keep tmux shelling centralized in `src/core/tmux.ts`. The default dashboard launcher creates/attaches/switches to `pi-agent-hub`; direct TUI mode is `pi-hub tui`. Dashboard tmux creation must run `tui` through the current CLI file via `cliTuiCommand` in `src/core/tmux.ts`, not bare `pi-hub tui`, so a Pi-installed entrypoint does not recurse into a stale global command on PATH. Inside-tmux managed-session attach uses native `switch-client` plus temporary guarded root bindings: `Ctrl+Q` returns to the dashboard, and `Alt+R` writes a dashboard action then returns into the selected session's rename dialog and switches back after a successful rename. No-prefix root bindings are tmux-server-global, so dashboard-only shortcuts must forward the original key sequence outside the dashboard rather than merely making the guarded action a no-op, and temporary binding sets must restore prior root bindings on cleanup. Return binding scripts can recreate the dashboard before returning and only restore previous bindings after a successful return switch; dashboard recreation must preserve `PI_CODING_AGENT_DIR`/`PI_AGENT_HUB_DIR` via `dashboardEnv()`. Outside-tmux direct TUI attach remains normal `tmux attach-session`. Dashboard and managed-session tmux chrome is configured there too: both override status/window styles and formats so global tmux themes do not leak in, derive colors from `src/core/chrome.ts` theme tokens when available, sync active managed status bars from the dashboard on load/theme changes, and keep managed status-right as `ctrl+q return · alt+r rename │ 📁 <session title> | <project>`.
- `SessionsController.refresh()` obtains one `tmux list-sessions -F '#{session_name}'` snapshot per refresh. `src/core/tmux.ts` reduces listed names to present/missing/unknown observations, retains unknown errors for status reduction, and prunes only explicit missing subagent/archive cascades. `createSessionTreeIndex()` supplies cached queue-based descendants for cascade work; callers still preserve raw, filtered, active, projected, and lane-local scope distinctions.
- Status explanations stay attached to their decision sources. `computeStatus()` emits structured runtime evidence from the reducer branch it takes, and the cockpit index emits placement evidence from the branch that assigns the owner tree's tier; the first active row in cached descendant order is the deterministic activity driver. `src/app/session-observation.ts` owns the shared read-only fleet observation used by controller refresh and `pi-hub explain`, including one bulk tmux snapshot and validated heartbeat reads. `SessionsController` exposes evidence only when its fingerprint still matches the row's tmux target, status, error, acknowledgement, and workflow; title, group, and order changes do not invalidate it. Missing evidence triggers the existing serialized refresh path before the workspace reveals evidence. The CLI observes the complete fleet once so owner/descendant placement matches the dashboard, but it never calls `updateRegistry()`. `src/tui/status-evidence.ts` is the single semantic wording builder for themed TUI and plain CLI output. `i` toggles evidence inside the selected-session action workspace. At 120+ columns that workspace is persistent; below 120 it is an ephemeral session-ID-bound full-width screen. Selection repair closes stale full-width state, and every rendered workspace action carries an exact catalog command ID. Workflow provenance remains a separate evidence fact and never becomes liveness or placement evidence.
- `src/tui/render-model.ts` owns the pure structural dashboard projection shared by rendering and `SessionsView` navigation. The view may reuse that projection for one registry/view-state snapshot, but volatile values such as current time, side-pane slots, and selection overlays are applied per render. Dialog modules receive family-specific narrowed action contexts; the flat action bag remains only at the composition boundary for compatibility. `renderForm()`, `renderDialog()`, and dashboard `box()` share a width-safe frame helper without changing their visual tokens.
- `src/tui/dashboard-commands.ts` is the shared pure catalog for catalog-owned direct keys, the `:` intent palette, dashboard Help, configured shortcuts, selected-workspace rows, and stable footer controls. Its fixed presentation order is selected-target actions, configured actions, sessions, named filters, then views/Help. Command descriptors carry stable namespaced IDs, every retained binding alias, search text, capability-dependent availability, and concise disabled reasons. Selected-target and configured-command IDs include the exact session identity; `SessionsView` rebuilds and revalidates that identity before execution, and forms/pickers retain the bound session/project through submission instead of consulting later selection. Disabled commands are discoverable but inert regardless of whether direct keys or the palette invoked them. Session search composes the bounded `matchesFilter()` fields and follows the unfiltered cockpit projection before appending hidden rows; it never searches pane output or Pi conversations. Session-result activation only selects and ephemerally reveals the exact current row, clears a fleet filter only when needed, and never attaches, restarts, or acknowledges. The ephemeral reveal can expose one collapsed/older Archived cascade or leave stage grouping for project grouping without persisting disclosure/grouping state, and clears on later navigation or view changes. Keep modal, text-editing, busy, full-width-workspace, pending-choice, tree-disclosure, and mouse precedence above normal command dispatch. Future action surfaces must consume the catalog instead of adding a parallel command table.
- The sidebar workspace is nested tmux attach inside the TUI's own window, not a new session model. `src/app/side-pane-lifecycle.ts` owns transient slot/focus snapshots, operation serialization, presence polling and reconciliation, user intents, full-screen handoff, panel and managed-session chrome synchronization, and teardown. It composes `src/app/side-pane.ts`, which remains the stateless low-level implementation for live inspection, geometry, repair, and pane mutation through `src/core/tmux.ts`; `src/app/run-tui.ts` supplies current session/theme/render context and forwards intents. Only non-dashboard panes whose tty maps to a `pi-agent-hub-*` client are Hub-owned content panes, and panel state is never persisted in the registry. Slots are fixed quadrants (`1` top-left, `2` top-right, `3` bottom-left, `4` bottom-right) tagged on live panes with `@pi_hub_slot`; inspection repairs missing or duplicate tags into the lowest free slots in geometry order. Layout is derived from occupancy, permits holes, and expands degenerate shapes rather than reserving blank regions. Bare `1`–`4` keys assign, replace, move, or swap panels; pressing the selected session's current slot again closes that panel. These keys never focus a panel, and every result remains sidebar-focused. `x` then `1`–`4` closes explicitly, `F` then `1`–`4` focuses from the TUI, and guarded `Alt+1`–`Alt+4` root bindings resolve and focus tagged panes at keypress time from anywhere in the dashboard session. `Alt+Q` returns from a panel to the sidebar, with `Ctrl+Q` retained as a fallback, while `o` rebuilds one selected panel or closes it when already alone. Explicit close, narrow-width refusal, and `o` reset also remain sidebar-focused. To avoid visible Pi conversation reflow, rebuilds pre-size each managed session window off-screen, create panes at their exact final dimensions, tag and title each pane, and restore every target to `window-size latest` only after the final split. Full-screen switching follows the same pre-size/switch/restore sequence; reset failures must remain observable, and a failed post-switch reset must not remove the active return binding. Live inspection supplies numbered `◫1`–`◫4` row indicators, a sparse four-slot sidebar strip built from the full unfiltered session list, matching pane titles, and the active quadrant. Theme-derived window-local pane options keep the focused border and reverse-color title badge accented while inactive borders/titles stay muted; opening and theme changes reapply them, while teardown unsets them. Single-click selects a row, double-click follows the width-aware `Enter` path, and wheel input moves selection. In junction density, visible continuation rows carry a mouse-only owner target with the same session identity as the title; this keeps keyboard navigation at one title target per card while making the whole visible card select/open consistently. Mouse input is dashboard-session scoped: enable tmux `mouse` only on `pi-agent-hub`, request SGR button reporting from the TUI pty, and unset the session override on quit. The lifecycle serializes presence inspection, panel mutation, focus, and full-screen handoff through one operation queue; it stops and drains polling before a full-screen switch. Shutdown prevents new pane intents from mutating tmux and drains queued or in-flight intents plus presence polling before restoring bindings and footers or closing panes. When managed panes exist, hide the outer dashboard status bar, hide each paneled managed session's session-scoped status footer, enable top pane borders, and install the guarded return/focus binding set. Side-pane geometry naturally keeps the sidebar in fleet-first width; it does not add a second preview-suppression state. Restore each managed footer before full-session handoff and when its panel closes or the dashboard shuts down; because footer visibility is session-scoped, full-session handoff also restores it in any retained panel for that target. Restore the dashboard chrome when no panels remain. The presence loop keeps the sidebar between 40 and 60 columns while managed panes exist: collapsed panes return to the 42-column default, oversized panes shrink to 60 columns (or less when needed to retain 40 content columns), and widths within that range remain user-controlled. Do not use tmux hooks or `select-layout`, which fight manual arrangements. Full-screen switching keeps any pane showing that target session; archiving closes only the pane showing the archived session. Dashboard quit closes all Hub-owned side panes before stopping the TUI. Do not target tmux window/pane indexes; use `$TMUX_PANE`, `#{pane_id}`, pane ttys, and `switch-client -c <tty>`.
- Keep extension loading idempotent. Managed sessions still pass `--extension` so linked CLI usage works without `pi install`; when the package is also installed, the extension may load twice in one Pi process. Suppress duplicate registration, but clear active process guards on `session_shutdown` so later sessions can register. The extension heartbeat is the generic bridge for live Pi session state such as active theme and workflow stage. Compaction lifecycle handling belongs here: `session_before_compact` publishes transient running state, normal `session_compact` restores the pre-compaction state, and `agent_start` keeps a continuing turn running; `willRetry` clears the snapshot/watchdog while leaving the session running until `agent_start`. Serialized heartbeat writes prevent a stale watchdog restore from overwriting a newer lifecycle state. The separate Hub-owned `theme-command.json` is a deliberately narrow one-time control bridge: parent extensions compare its timestamp/revision to process start, resolve the concrete global theme through Pi, apply a `Theme` object without rewriting settings, and heartbeat immediately; subagents and older commands are ignored. The workflow producer owns each ordered `WorkflowSnapshot.steps` definition, state-change timestamp, optional active-mode display, and optional `currentStepComplete` boolean. Hub validates the base workflow and each decoration independently but mirrors no step ids, short codes, labels, mode vocabulary, or legacy fallback; invalid decoration does not hide a valid base workflow. One pure positional marker rule serves compact rows, junction cards, and the action workspace: indexes before `activeIndex` are complete; the current index is complete only when `currentStepComplete === true`, otherwise active; later indexes are pending. Direct later-step invocation therefore checks earlier positions. This is a position cue rather than sequence enforcement or an execution audit. Completion does not change lane placement, and retained terminal snapshots remain visible across stale/shutdown state until a new workflow snapshot replaces them. Base workflow state may be retained in `registry.json`, but `SessionsController` merges a mode only into `RuntimeSession` from a fresh non-shutdown heartbeat with confirmed tmux presence, so modes never affect persistence or liveness.
- Managed-session lifecycle orchestration lives in `src/app/session-lifecycle.ts`; it owns add/start/stop/restart/fork, delete, subagent cleanup, and worktree finish/discard sequencing while reusing core adapters. `src/app/delete-session.ts` and `src/app/worktree-session.ts` remain explicit safety entry modules for delete and Git lifecycle flows and delegate to the central module; callers must keep using those entry paths. Normal delete stops tmux, removes any owned multi-repo workspace, removes the registry row, removes the heartbeat, and keeps Pi conversation/session files. Normal delete intentionally keeps hub-owned worktree directories; finish or discard worktree sessions after a clean-state preflight, then merge/remove or discard all session worktrees before removing registry rows and heartbeats. Multi-repo worktree finish/discard handles additional repos before the primary repo so partial failures keep the primary session cwd recoverable. Tmux, workspace, and Git work that determines a lifecycle mutation stays outside the lock and completes before the short registry update; after the registry commit, remove each session's heartbeat. `removeSessions(sessions, path, env)` filters only prepared IDs from the latest registry after tmux/workspace cleanup. Successful deletion removes only the prepared IDs from latest state, while partial worktree failure transforms the latest surviving parent after failed external work. Archive pruning is separate and dashboard-only after seven days: `src/app/controller.ts` removes expired archived registry rows plus heartbeat and owned multi-repo workspace state only after every row in the session/subagent cascade is confirmed missing from tmux. Refresh observes one tmux session-list snapshot for its initial registry and applies an observation only to a latest row with the same session ID, tmux target, and unchanged `updatedAt` version before projecting runtime fields or pruning. The TUI still pauses its local refresh loop around deletion/finish/discard for lifecycle ordering, while latest-state registry transformations independently preserve concurrent CLI, TUI, and external subagent writes.
- Groups are implicit flat labels on sessions, not separate records. Creating a session with a new group label creates the group; pressing `g` in the TUI moves the selected session to an existing or new group, while `G` renames the selected session's current group for all sessions in that group. Pressing `K`/`J` or Shift-Up/Shift-Down reorders the selected Active or Backlog session within its current group; Archived is globally chronological and cannot be manually reordered. Pressing `A`, `B`, or `U` archives, backlogs, or restores a parent session by updating optional `ManagedSession.bucket` / `bucketChangedAt` fields; these actions never stop tmux/Pi, and subagent rows inherit their top-level parent's effective lifecycle instead of moving directly. Archived shows the five newest parent cascades by default and exposes older cascades through an ephemeral disclosure target. In the project cockpit, Backlog is row metadata rather than a section header. Archived remains a synthetic selectable target; `Enter` and double-click toggle its persisted collapse state, while filtering reveals matching rows without mutating that state. The Archived header is a non-session target, so session actions remain inert; collapsing it repairs a hidden session selection to the header. Pressing `R` sends exact `/name <text>` to a live Pi session through the cursor-aware form used by in-session `Alt+R`; stopped/error rows require restart first. Normal name propagation updates the Hub cache. `N` remains manual recovery from the latest persisted Pi `session_info` name. In-session `Alt+R` keeps the explicit dashboard rename dialog because that flow temporarily leaves the managed session before switching back. Pressing `p` sends a one-line footer prompt to the selected live session through tmux paste without opening it. At 120+ columns, pressing `Enter` on a stopped or error row restarts it instead of attempting to attach. Below 120, the first `Enter` opens the exact selected action workspace without side effects and `Enter` inside runs that restart action. Pressing `r` opens restart choices: `r` resumes the selected saved Pi conversation, `n` clears the selected hub row's Pi session metadata and starts a new Pi conversation in the same tmux/session record, and `a` restarts all active non-subagent sessions while skipping Backlog and Archived. Do not add separate empty-group lifecycle unless the model changes.
- Active and Backlog source rows retain stable `default`-first group order. Inside each group, errors come first, then unacknowledged `waiting` rows newest-first, `starting`/`running`, acknowledged `waiting`/`idle` rows by activity, and stopped rows. The project cockpit then stable-partitions complete owner trees into its presentation tiers without changing that source order inside a tier; groups are muted row metadata rather than headings. `ManagedSession.order` is optional registry data, breaks exact priority/activity ties, and falls back to group-relative registry order; new/forked/group-moved sessions append to the target group within the current lifecycle section. `K`/`J` reorder only inside the selected row's current tie. `src/core/session-order.ts` owns this ordering while keeping Archived globally newest-first by archive time; every nonempty cockpit tier renders its heading. `src/core/session-tree.ts` builds on `src/core/session-order.ts` and owns both recursive subagent nesting and canonical ancestry lookup for navigation and render projections. Build one `createSessionTreeIndex()` per behaviorally meaningful row scope and reuse its cached trace; do not merge filtered, active, projected, lane-local, or raw-snapshot scopes. The index supplies ownership, depth, and linked-parent facts, while each projection applies its own unresolved-ancestry policy: archive lifecycle falls back to the row when a parent is missing; the project cockpit keeps missing-parent and cyclic terminal rows as standalone presentation owners; board lane and expansion ownership omit ownerless subagents; and archive lifecycle plus board grouping use the terminal cycle member. Titles never affect order, and stopped sessions remain in the group instead of rendering in a separate subsection.
- The selected-session action workspace uses only validated producer context, current runtime projections, workflow/status evidence, and catalog command descriptors. Hub does not capture, store, render, or search tmux pane tails or Pi conversation content. `src/app/refresh-loop.ts` refreshes observation state only; `SessionsController` has no preview snapshot or capture invalidation path.
- Keep rendering pure and testable in `src/tui/*`; ANSI styling must stay width-safe via theme helpers. `v` toggles density between compact rows and all-session junction cards; `S` toggles between the project attention cockpit and workflow-stage lanes. The project cockpit classifies complete owner trees from the full unfiltered fleet in strict order: explicit waiting/idle owner attention → `NEEDS YOU`, owner error → `HEALTH`, starting/running owner or descendant → `ACTIVE`, other non-archived owners → `QUIET`, while lifecycle-owned `ARCHIVED` stays separate. Descendants inherit placement without changing their own state, and filtering changes visibility only. Project rows reveal `backlog`, group, workflow short, and activity age by available width after reserving prefixes, badges, and a readable title; Archived rows remain age-only. Lifecycle still controls row/card richness and glyph treatment. In stage grouping, lane headers and producer workflow-tree projection apply independently of card density. Dashboard rendering must be safe at any pane size: `SessionsView.render()` owns the below-40-col narrow notice, `renderSessions()` bounds output to terminal height, and mouse hit maps must describe only visible rows. The stage-grouping projection reuses `RenderSection`: it chooses one deterministic producer pipeline from filtered Active parents, keeps compatible trees in producer lane order, then appends synthetic `OTHER ACTIVE` for every workflowless or incompatible Active parent tree. Backlog/Archived stay footer-only. Every section nests rows under the top-level parent's existing group; headings count parents only and no row repeats its group. Subagent descendants are omitted by default through separate ephemeral project/stage `SessionsView` expansion sets. `←`/`→` collapses or expands the selected top-level tree; `Shift+←`/`Shift+→` applies to every tree in the current grouping; `Space` remains a stage-group selected-tree toggle. `▸`/`▾` reflects projection state, collapsing a selected descendant repairs selection to its parent, and an active filter reveals matching tree context without mutating either set. Only visible children receive row targets. Optional producer modes substitute active-step display without entering pipeline identity or lane selection; stopped rows suppress mode decoration while retaining their base lane. Top-level parent rows derive `⚙︎N` from descendant subagents currently `starting` or `running`; the count is transient, omitted at zero, and never promotes child runtime or attention. Compact density keeps every session one line. For waiting/idle rows in both grouping modes, normalized producer attention uses `✓`, `?`, or `!`; compact rows reuse the prefix cell and junction density places attention beside the branch. Running/error/stopped presentation remains authoritative, and attention is projected per row without parent promotion. Junction cards keep Pi-native cached titles and show a label-free `#ticket-id · subtitle` row plus workflow markers (`✓` done, `◉` active, `·` pending); task grids use `plan.phases` separators when present and fall back to whole-plan task totals when absent. The grid adapts from separated phases to a flat grid, then to a ten-cell ratio plus count before dropping at the narrowest width. The progress line is implementation-plan state, not workflow position: producer activity takes precedence, while an absent activity shows this deterministic grid without interpreting a producer activity id. Project rows place an accented `⎇` before worktree titles and a dim `⧉ N` after multi-repo titles; the action workspace retains the full branch and compact repository count. The optional mode short and `⚙︎N` are reserved before title truncation. All-session density renders tier-owned `├`/`└` junctions in the project cockpit and group-owned junctions in stage lanes, with selected `┣`/`┗` branches and full-span `selectedBg`. Only Active main sessions add optional ticket/subtitle and producer activity-or-progress lines; missing fields collapse, Backlog and subagents stay one line, and Archived remains flat. Its height window always keeps the selected title. When capacity permits, it retains selected continuation lines and the owning section/group context, then fills remaining capacity with nearby title targets before count indicators. Spare rows can restore a nearby card's continuation lines only when that card's title is visible. Each continuation retained by windowing carries a mouse-only owner target; hidden or orphaned lines never create hit targets, and title targets remain the sole keyboard/navigation targets. At 120–159 columns the action workspace reserves 34 cells; at 160+ it reserves 44 cells. It renders selected identity, explicit request, Hub-derived maintainer recommendation, enabled catalog actions, bounded producer context, runtime state, optional evidence, producer workflow, and tree context in that order. At 40–119 columns `Enter`, `i`, or session-row double-click opens the same renderer full-width. Short-height compaction preserves a primary action, recommendation, and requested evidence without leaving hidden hit targets. The Archived disclosure remains a synthetic non-session target. The selected row/span uses `selectedBg` after padding, and footer strings stay plain in the render model for `layout.ts` to style. At sidebar width, show labeled primary controls plus `? Help`. Pressing `t` opens the dedicated theme dialog over built-in and global Pi theme resources. Preview updates `SessionsView`, dashboard status chrome, and sidebar borders only; `Escape` restores and `Enter` persists.
