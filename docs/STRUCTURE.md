# pi-agent-hub Structure

`pi-agent-hub` is a minimal TypeScript package for managing Pi coding-agent sessions in tmux. It is Pi-only: Pi remains the agent runtime, tmux remains the process substrate, and this package supplies the dashboard/registry glue.

## Layout

```text
src/
  cli.ts                 command entrypoint (`pi-hub`; `pi-agent-hub` remains an alias)
  index.ts               public exports
  app/                   dashboard launcher, controller, refresh loop, and shared session actions for the standalone TUI
  core/                  shared heartbeat intake, JSON store/locking, registry, paths, tmux, Pi process args, status reducer, multi-repo workspace and worktree helpers
  extension/             tiny Pi extension for session heartbeats
  mcp/                   MCP catalog/project config, direct clients, pool, tool adapter
  skills/                project skill attach/detach and pool discovery
  tui/                   pure render model, terminal layout, dialog modules, shared text/form primitives, picker, and theme helpers
test/                    Node test-runner tests compiled by TypeScript
package.json             npm package metadata, SemVer version, CLI bins, and Pi extension declaration
CHANGELOG.md             npm/GitHub release notes, maintained per published version
docs/STRUCTURE.md        this developer onboarding guide
docs/FEATURES.md         user-facing feature map and dashboard workflow
docs/CONFIG.md           runtime state, global config, themes, Skills/MCP setup
docs/DEVELOPMENT.md      local setup, tests, package checks, smoke testing, release workflow
docs/history/             archived feature notes; useful context, not current product contracts
```

## Runtime state

- Global state lives under `PI_AGENT_HUB_DIR` or `<PI_CODING_AGENT_DIR>/pi-agent-hub`.
- Optional global config lives at `config.json`; it can set skill pool directories, the MCP catalog path, a managed-session `session.prelude` shell snippet, and `session.worktreeDefault` for new-session forms.
- The session registry is `registry.json`; `ui-state.json` persists fleet/board `grouping` (`project`/`stage`), the independent `fleetGrouping` choice (`status`/`repo`, default `status`), the normalized dashboard filter (text plus an ordered lifecycle array), HEALTH/ACTIVE/QUIET/ARCHIVED cockpit collapse preferences, the bounded first-run onboarding phase, and one dismissed release-cue ID. `NEEDS YOU` and `NEW` are never persisted as collapsed. A missing state file plus an empty initial registry creates and immediately writes the new-user cohort; a missing file with a nonempty registry remains an existing-user state. Malformed or unsupported saved fields are ignored while valid fields survive. Repo folds, card richness, responsive widths, tree disclosure, tier navigation and filtered reveals remain ephemeral.
- `pi-hub` opens a stable dashboard tmux session named `pi-agent-hub`; use `pi-hub tui` to run the TUI directly without the dashboard wrapper. The `pi-agent-hub` command remains available as a compatibility alias.
- Managed Pi sessions write heartbeat files under `heartbeats/<session-id>.json` through the extension. `src/core/heartbeat.ts` reads each file as unknown data, requires a valid liveness envelope and a `managedSessionId` matching the requested file, then normalizes optional identity, theme, context, and workflow data before dashboard use. A malformed envelope is treated as a missing heartbeat; malformed optional metadata is omitted without hiding valid liveness. Unknown producer fields remain compatible. Each valid heartbeat can include Pi's native session name, the latest valid producer-neutral `pi-agent-hub-context` snapshot, and optional producer-owned workflow runtime. The registry title caches nonblank heartbeat names. Initial names follow [Session names](FEATURES.md#session-names): allocate collision suffixes inside the registry update lock and pass the result through `buildPiArgs` as Pi's native `--name` only for forks, which otherwise inherit the source name. New conversations and resumes start without `--name`; the registry title is the local fallback until a heartbeat reports a Pi name. Keep later naming producer-owned rather than reapplying defaults from Hub. Generic subtitle, description, and attention remain runtime-only. The independently validated optional generic `worktree` field carries producer-neutral lifecycle evidence. Hub retains only that bounded snapshot, guarded by Pi conversation, producer/record identity, and monotonic revision; restart-new rejects the outgoing Pi identity until a replacement arrives. Hub-owned mappings remain authoritative and derive active state without a duplicate persisted snapshot. Workflow activity and deterministic plan progress travel inside `workflow-runtime`; Hub does not read producer files or a metadata sidecar.
- Optional `pi-tmux-subagents` compatibility uses flat registry rows with `kind: "subagent"`, `parentId`, `agentName`, `taskPreview`, and `resultPath`; the dashboard renders those rows as nested micro rows with bounded agent name and task preview; the same task preview remains available to the action workspace and filtering. Standalone subagent state remains owned by `pi-tmux-subagents`, and dashboard refresh prunes subagent rows whose tmux sessions are gone so stale completed rows do not linger.
- Managed tmux sessions use the `pi-agent-hub-<first-12-session-id-chars>` name. If `session.prelude` is configured, it runs inside the managed tmux shell before `exec pi`; dashboard launch and direct `pi-hub tui` do not run it.
- Multi-repo sessions keep `ManagedSession.cwd` as the primary repo and start Pi from `<global-state>/workspaces/<session-id>`, a symlink workspace containing the primary repo, each additional repo, and `.pi -> <primary>/.pi`. Every managed parent launch, including the direct normal-session fork path, exports `PI_AGENT_HUB_PRIMARY_CWD=ManagedSession.cwd`; it never exports `workspaceCwd` or an additional repo through that variable. This gives producer extensions one optional process-local project root when resumed conversation history retains a different Pi header cwd, without persisting the path or changing normal `f`/worktree behavior. If selected repo roots contain `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, or `CLAUDE.MD`, Hub generates a workspace-root `AGENTS.md` that labels and embeds those repo instructions so Pi loads them from the workspace cwd.
- Hub-owned worktree sessions keep `ManagedSession.cwd` as the primary worktree path and store metadata in the registry. New rows use `worktrees[]` with one entry per repo (`path`, source `repoRoot`, branch, base branch, role), while scalar `worktreePath`/repo/branch fields remain compatibility metadata. Worktrees live under `<global-state>/worktrees/<repo-name>/<session-id-prefix>-<branch-slug>`. At process start, `src/core/worktree-context.ts` validates the complete mapping and supplies one bounded guidance string to the Hub extension and the optional `pi-tmux-subagents` prompt bridge. The extension appends that guidance to each parent turn through `before_agent_start`; child launchers receive the same text through their package-owned boundary instead of loading Hub state.
- Recent directory choices for the new-session picker live in `<global-state>/repo-history.json`; current registry paths are merged with this bounded history at TUI startup. Named ordered directory sets live separately in `<global-state>/session-favorites.json`, use stable IDs and atomic locked mutations, and never store group overrides or worktree settings. Applying a favorite copies its directories into the draft and seeds the editable Group from its name without launching a session.
- Project skill state lives in `<project>/.pi/sessions/skills.json`; available skills come from `skills.poolDirs` in global config or `<global-state>/skills/pool`.
- Project MCP enablement lives in `<project>/.pi/sessions/mcp.json`; available MCP servers come from the configured catalog path or `<global-state>/mcp.json`.
- JSON state files use `src/core/atomic-json.ts` for atomic writes, optional version/shape parsing, shared errno checks, and lock-dir guarded read-modify-write updates. `src/core/registry.ts` owns registry freshness: `loadRegistry()` reads state, while `updateRegistry()` is the sole registry write path. Registry updates compare their persisted JSON snapshot inside the lock and skip the atomic write when it is unchanged; other JSON stores retain their configured write behavior.
- In the standalone TUI, `<project>` for Skills/MCP pickers is the selected session's primary cwd, with dashboard cwd as the fallback when nothing is selected. For multi-repo sessions, Skills/MCP state applies to the primary repo only.
- Pooled MCP uses a Unix socket at `<global-state>/pool/pool.sock`; run `pi-hub mcp-pool` explicitly when pooled servers are enabled.
- Inside-tmux switch return state lives under `return-key/` while the temporary `Ctrl+Q` binding is active; `Alt+Q` remains available to Pi for message editing. `pi-hub doctor` reports active/stale return state.

## Design rules

- Keep public names centralized in `src/core/names.ts`; `pi-hub` is the primary CLI command, `pi-agent-hub` is a compatibility alias, and runtime state/tmux names remain `pi-agent-hub`. CLI install diagnostics live in `src/core/install-diagnostics.ts`: they may warn and report exact PATH fixes, but must not mutate PATH, shell profiles, npm globals, or Pi package directories.
- Keep heartbeat shape and identity checks centralized in `src/core/heartbeat.ts`. Producer `workflow-runtime` entries identify position with `activeStep`, while persisted heartbeat workflows use `activeIndex`; separate adapters share step and decoration checks and must not accept the other position shape. The extension owns publication timing and atomic serialized writes. Keep liveness reduction and retention centralized in `src/core/status.ts`, and keep registry/runtime projection in `src/app/controller.ts`; neither layer reparses heartbeat metadata. The TUI acknowledges a `waiting` session before attach/switch so opening it clears the unread/waiting indicator; keep that ordering when changing attach behavior. Pi's coalesced `ui_prompt_start` / `ui_prompt_end` span temporarily publishes `waiting` and restores the prior state only while a monotonic lifecycle revision still belongs to that prompt; newer same-state or different-state lifecycle events invalidate restoration. Fresh managed-session heartbeats can also carry the active Pi theme snapshot used by that session's managed tmux chrome; stale or shutdown heartbeats must clear it so disk settings remain the per-session fallback. Dashboard theming is independent: synchronized mode reads Pi's global theme setting, detached mode reads Hub's override, and neither follows a heartbeat/session anchor. The heartbeat `workflow` snapshot (bridged from the optional workflow-runtime extension; see CONFIG.md) is the deliberate contrast: it is state about the work, not live chrome, so `applyComputedStatus` adopts it from fresh heartbeats but retains the last known value across stale/shutdown heartbeats — a stopped-but-Active session remains eligible for its board lane. The latest heartbeat `stateSince` is retained as `lastActivityAt`; compaction heartbeats use the pre-compaction `stateSince` so transient green compaction activity does not make an old session newly recent. `workflow.updatedAt` is the producer's state-change timestamp and may advance within one step, while heartbeat `updatedAt` remains the independent liveness timestamp.
- Keep tmux shelling centralized in `src/core/tmux.ts`. The default dashboard launcher creates/attaches/switches to `pi-agent-hub`; direct TUI mode is `pi-hub tui`. Dashboard tmux creation must run `tui` through the current CLI file via `cliTuiCommand` in `src/core/tmux.ts`, not bare `pi-hub tui`, so a Pi-installed entrypoint does not recurse into a stale global command on PATH. Inside-tmux managed-session attach uses native `switch-client` plus a temporary guarded `Ctrl+Q` root binding to return to the dashboard; `Alt+Q` is never intercepted because Pi uses it to edit the last message. `Alt+R` writes a dashboard action then returns into the selected session's rename dialog and switches back after a successful rename. `Alt+W` writes a `next-request` action through the same return script; the dashboard opens the first NEEDS YOU owner other than the origin through the normal `Enter` path, so acknowledgement and pin focus stay in one place. No-prefix root bindings are tmux-server-global, so dashboard-only shortcuts must forward the original key sequence outside the dashboard rather than merely making the guarded action a no-op, and temporary binding sets must restore prior root bindings on cleanup. Return binding scripts can recreate the dashboard before returning and only restore previous bindings after a successful return switch; dashboard recreation must preserve `PI_CODING_AGENT_DIR`/`PI_AGENT_HUB_DIR` via `dashboardEnv()`. Outside-tmux direct TUI attach remains normal `tmux attach-session`. Dashboard and managed-session tmux chrome is configured there too: both override status/window styles and formats so global tmux themes do not leak in, derive colors from `src/core/chrome.ts` theme tokens when available, sync active managed status bars from the dashboard on load/theme changes, and keep managed status-right as `ctrl+q return · alt+r rename │ [⚑ N need you · alt+w next │ ]📁 <session title> | <project>`. Clients narrower than 80 columns get `[⚑ N │ ]📁 <session title> │ ⌂ hub` instead, because tmux cuts long status-right text from the left. Both return hints are a tmux 3.4+ `range=user|pi-hub-return`; the handoff's guarded return binding also wraps `MouseDown1Status` so a tap on that range runs the same return script, and every other status click runs the saved previous binding. Older tmux ignores the range and keeps the text. Taps need the user's tmux `mouse on`; Hub never enables mouse in managed sessions. Labels inside the width conditional escape `,` and `}`. The bracketed part is a tmux conditional on the per-session user option `@pi_hub_needs`, so count changes need one `set-option` instead of a chrome resync; branch text must not contain commas.
- `SessionsController.refresh()` obtains one `tmux list-sessions -F '#{session_name}'` snapshot per refresh. `src/core/tmux.ts` reduces listed names to present/missing/unknown observations, retains unknown errors for status reduction, and prunes only explicit missing subagent/archive cascades. `createSessionTreeIndex()` supplies cached queue-based descendants for cascade work; callers still preserve raw, filtered, active, projected, and lane-local scope distinctions.
- Status explanations stay attached to their decision sources. `computeStatus()` emits structured runtime evidence from the reducer branch it takes, and the cockpit index emits placement evidence from the branch that assigns the owner tree's tier; the first active row in cached descendant order is the deterministic activity driver. `src/app/session-observation.ts` owns the shared read-only fleet observation used by controller refresh and `pi-hub explain`, including one bulk tmux snapshot and validated heartbeat reads. `SessionsController` exposes evidence only when its fingerprint still matches the row's tmux target, status, error, acknowledgement, and workflow; title, group, and order changes do not invalidate it. Missing evidence triggers the existing serialized refresh path before the workspace reveals evidence. The CLI observes the complete fleet once so owner/descendant placement matches the dashboard, but it never calls `updateRegistry()`. `src/tui/status-evidence.ts` is the single semantic wording builder for themed TUI and plain CLI output. `i` appends or hides useful evidence inside the selected-session action workspace. At 120+ columns that workspace is persistent; below 120 it is an ephemeral session-ID-bound full-width screen. Selection repair closes stale full-width state, and every rendered workspace action carries an exact catalog command ID. Workflow provenance remains a separate evidence fact and never becomes liveness or placement evidence.
- `src/tui/render-model.ts` owns the pure structural dashboard projection shared by rendering and `SessionsView` navigation. The view may reuse that projection for one registry/view-state snapshot, but volatile values such as current time, side-pane slots, and selection overlays are applied per render. Effective repo folds, filtered headers and archive-disclosure visibility must come from this shared projection; rendering and keyboard navigation must not independently reconstruct them. Mouse, keyboard and selection repair use the same exact-target selection path. Synthetic headers cannot open session actions, evidence or a hidden workspace. Dialog modules receive family-specific narrowed action contexts; the flat action bag remains only at the composition boundary for compatibility. `renderForm()`, `renderDialog()`, and dashboard `box()` share a width-safe frame helper without changing their visual tokens.
- Fleet grouping is independent of the workflow board: `v` switches Status/Repo and `S` visits the board without losing that choice. Repo sections partition complete owner trees by normalized primary source path, using Hub worktree source metadata when present; additional repos do not duplicate rows. Use the full fleet for identity labels and collision disambiguation, not filtered rows. Keep alphabetical repo order and stable cockpit-tier order within each repo, with Backlog metadata and a separate chronological Archived section. Full-fleet owner requests and hidden child requests remain separate counts, never parent-state promotion. Repo folds are ephemeral; filters initially expose matches, then accept temporary folds. Changing or clearing the filter drops those temporary folds without changing the unfiltered layout. Exact reveals expose rows without changing folds. Preserve selected session identity across view changes when eligible, and repair vanished headers to a visible target. Repo-mode manual reorder is unavailable. Do not introduce repository records, filesystem discovery, or a second renderer for this presentation.
- `src/tui/cockpit-onboarding.ts` owns bounded normalization and pure transitions for the persisted first-run cohort, exact explicit-request trip, completion, and versioned release-cue dismissal. `src/app/run-tui.ts` classifies a new user only when `ui-state.json` is missing and the initial registry is empty; all other users receive only the current release cue. `SessionsView` starts the trip only after exact question acknowledgement plus successful pin focus or full-screen handoff, and completes it only after canonical `Ctrl+Q` returns successfully. Sidebar return completes directly; full-screen return writes a typed `{ action: "return", key: "ctrl-q" }` dashboard-action receipt after `tmux switch-client` succeeds. Locate, manual acknowledgement, failed routing, and attention without a request ID do not advance it. Coaching and the synthetic release row are presentation-only, suppressed outside normal unfiltered Status mode, and never enter fleet counts or session actions. UI-state writes serialize complete snapshots. Shutdown first drains active side-pane and dashboard-action producers, then drains the UI-state writer, so a late transition or stale write cannot overwrite completion or dismissal.
- `src/tui/dashboard-commands.ts` is the shared pure catalog for catalog-owned direct keys, the `:` intent palette, dashboard Help, configured shortcuts, selected-workspace rows, and stable footer controls. Its fixed presentation order is selected-target actions, configured actions, sessions, named filters, then views/Help. Command descriptors carry stable namespaced IDs, every retained binding alias, search text, capability-dependent availability, and concise disabled reasons. Selected-target and configured-command IDs include the exact session identity; `SessionsView` rebuilds and revalidates that identity before execution, and forms/pickers retain the bound session/project through submission instead of consulting later selection. Disabled commands are discoverable but inert regardless of whether direct keys or the palette invoked them. Session search composes the bounded `matchesFilter()` fields and follows the unfiltered cockpit projection before appending hidden rows; it never searches pane output or Pi conversations. Session-result activation only selects and ephemerally reveals the exact current row, clears a fleet filter only when needed, and never attaches, restarts, or acknowledges. The ephemeral reveal can expose one collapsed/older Archived cascade or leave stage grouping for project grouping without persisting disclosure/grouping state, and clears on later navigation or view changes. Keep modal, text-editing, busy, full-width-workspace, pending-choice, tree-disclosure, and mouse precedence above normal command dispatch. Future action surfaces must consume the catalog instead of adding a parallel command table. Help consumes catalog base labels and primary keys as a static reference, independent of selected-session availability. Its Session actions, Pins, Views, and Filters sections place complete keys at the right, hide compatibility aliases, and name palette-only filters with one `via : palette` note. At 160+ columns, paired sections shorten the page; smaller widths use one column.
- `src/app/attention-delivery.ts` owns the pure process-local transition from validated producer attention to transient delivery. Producers supply optional bounded request IDs; Hub seeds current identities silently at startup, deduplicates by session plus request ID, persists no delivery history, and expires each active entry after six seconds. `src/app/run-tui.ts` owns best-effort effects after successful refresh: only the managed dashboard tmux session can inspect clients, send literal-safe six-second messages, emit the opt-in BEL, write the opt-in OSC 9 desktop notification to each delivered client's tty, or set `@pi_hub_needs`. Counts come from `otherRequestCounts()` (NEEDS YOU owners minus self, only for parents with confirmed tmux presence), are written on change through one serialized chain, re-asserted every 15 s because restarted tmux sessions lose user options, and cleared on shutdown after that chain drains. Per-client routing suppresses the exact cockpit pane, managed session, or requesting pin; any suppressed client disables the process-wide BEL without blocking text to other eligible clients. `SessionsView` receives bounded active presentation data, revalidates the exact request before locate or acknowledgement, and keeps global locate/bell commands independent from synthetic or missing selected-row targets. Rendering and tmux adapters sanitize producer text through `src/core/terminal-text.ts`; neither layer detects transitions or persists state.
- The sidebar workspace is a set of nested tmux attaches inside the dashboard window, not a second session model. `src/app/side-pane-lifecycle.ts` is the sole serialized boundary for presence, assignment, focus, resize, handoff, chrome, and shutdown; `src/app/side-pane.ts` owns stateless inspection, topology, repair, rollback, and pane mutation through `src/core/tmux.ts`. Canonical state is one sparse four-slot projection. `@pi_hub_slot` is transient pane metadata only; every operation also validates pane ID plus tty-to-`pi-agent-hub-*` managed identity, repairs missing/duplicate tags deterministically, reconciles duplicate attaches, and ignores user panes. Bare `1`–`4` assigns the exact selected live session to a free slot, `P` chooses the lowest free slot or focuses its existing slot, `x` closes that selected identity, and occupied destinations refuse without retarget, swap, replacement, acknowledgement, or eviction. Guarded `Alt+1`–`Alt+4` focuses slots from anywhere in the dashboard session; guarded `Alt+Left`/`Alt+Right` remain optional spatial focus, and only `Ctrl+Q` returns to the cockpit. `Alt+Q`, `Alt+Up`, and `Alt+Down` remain available to Pi for message editing; Pi uses `Alt+Up` to edit queued messages. Root bindings target the saved sidebar pane with an intent, pass the original key outside the dashboard, and restore prior server-global bindings. Whole-window capacity counts pins, not slot numbers: zero below 100 columns, two pins in any slots at 100–159, and four at 160+. Width contraction preserves every existing slot, marks the layout constrained, and blocks additions/resizing while still allowing safe close and rollback. Phone and desktop clients share the dashboard window, so below 100 window columns the presence loop hides existing pins behind a Hub-made zoom of the dashboard pane, turns the pane-border title row off, and reports `hidden`. Pins stay attached. Queued focus, pin, and close operations treat pins as hidden from the fresh window width, even before the presence loop zooms. While hidden, slot focus and existing-pin `P` hand off full screen, exact-session focus and spatial focus report unavailable, and close kills only the pin pane without a rebuild. At 100+ columns Hub unzooms only a zoom it made, restores the border, and rebuilds pins from the last wide sidebar width and split; it never undoes a user zoom and never resizes a full-window dashboard pane. Any two pins stack in slot order below 120; at 120+ slots 1–2 alone sit side by side, while any slot above 2 uses the full-slot topology, which uses columns `1/3` and `2/4`, expands holes, and keeps 1/3 or 2/4 resizing on the vertical axis. `+`/`-` changes the topology's main split in ten-point steps clamped to 30/70. Rebuilds pre-size every target at final geometry, split at final size, tag/title the pane, and restore `window-size latest`; only confirmed vanished targets are ignored, while other preparation errors enter rollback and prior attachments are restored before the error surfaces when possible. Pin creation keeps cockpit focus and does not acknowledge; explicit pin/slot/spatial focus and full-screen handoff reveal the exact row and acknowledge waiting state before focus. Open in Pi routing for questions uses a serialized exact-session focus operation: it re-inspects live pins by tmux target, then reveals, acknowledges, and focuses that target, or returns unavailable so SessionsView can use normal full-screen attach. It never carries a stale slot number across the operation. Rendering derives only from the sparse slot projection: rows use `▢N`/`▣N`, the `PINNED FLEET` header shows only the pin count and a `constrained` warning, pane titles use `LIVE N · <title>` with optional owner/ticket context, and the narrow cockpit keeps the decision/evidence strip. Restore the target managed footer when its pin closes or before its full-screen handoff. Keep shared dashboard status, pane-border chrome, and pin bindings active while any pin remains; restore them after the final close or during shutdown. Pane-border chrome also marks the focused pane: its title carries a `⌨` marker in reversed accent, and `pane-border-lines heavy` thickens every border so the accent-colored focused outline reads against the dim inactive lines. Do not tint inactive panes with `window-style`; Pi paints its own message and tool panels, so a tint produces an inverted patchwork. The heavy lines are unset with the border chrome. Keep the sidebar between 40 and 60 columns, use the approved 38-cell minimum for side-by-side pins, avoid tmux hooks and `select-layout`, and never target tmux pane indexes.
- Follow view (`o`) is the one retargeting exception, built on the same pin machinery rather than a second pane model. It is a single slot-1 pin plus the transient dashboard-window option `@pi_hub_follow`; rebuilds and rollbacks never touch window options, so hidden-zoom restore keeps it. `following` holds only while that flag is set and exactly one pin exists; presence clears a flag left without its pane, and the first real pin clears a stale one. It needs a live selection, no pins, and 100+ columns; while following, pin assignment/close/resize and Conversation are refused, and the lifecycle also refuses non-follow placement. `SessionsView` schedules `retargetFollow` once the exact live selection has been stable for 200 ms; non-live and synthetic selections cancel and keep the shown session, whose pane title then names the selected row's state. The serialized `retarget` re-checks that its target is still the selected live session, skips while hidden, pre-sizes the target, runs `switch-client -c <pane tty>`, and always restores `window-size latest`, also after a failed switch. It never reveals, acknowledges, or touches; if the follow pane is focused, its new identity is recorded so presence does not treat it as a focus. On restore from hidden it retargets once to the current selection. While following a live row, the catalog lists `focus-follow` ahead of `open`, so `Enter`/double-click run one serialized operation that retargets if needed, reveals, acknowledges, and focuses the pane; `open` loses its Enter binding and keeps full-screen palette/workspace routing, bypassing pinned-question focus. Stopped/error rows keep `open` (restart). Rendering uses `FOLLOWING`, no pin count except `follow view hidden`, `LIVE · <title>` pane titles, and a follow footer. `SessionsView` keeps an ephemeral follow-wanted flag, seeded from `dashboard.followDefault` (default on) and set by `o` and the palette default toggle. While it is set and the pane is absent (startup, or archive detach / tmux exit after stop or delete), the same settle timer calls `follow` for the exact live selection when no pins, Conversation, or busy action exist and capacity allows; a refusal is not retried until the selection changes.
- Keep extension loading idempotent. Managed sessions still pass `--extension` so linked CLI usage works without `pi install`; when the package is also installed, the extension may load twice in one Pi process. Suppress duplicate registration, but clear active process guards on `session_shutdown` so later sessions can register. The extension heartbeat is the generic bridge for live Pi session state such as active theme and workflow stage. Compaction lifecycle handling belongs here: `session_before_compact` publishes transient running state, normal `session_compact` restores the pre-compaction state, and `agent_start` keeps a continuing turn running; `willRetry` clears the snapshot/watchdog while leaving the session running until `agent_start`. Serialized heartbeat writes prevent a stale watchdog restore from overwriting a newer lifecycle state. `Shift+F` passes one attempt token through `PI_AGENT_HUB_FORK_COMPACT`. Hub and Rules capture it at registration and consume it at session start, since CLI `pi --fork` reports `startup`, not a native fork boundary. Rules owns the durable ticket/workflow reset. Hub requires the matching `workflow-runtime-reset` receipt and cleared producer state before compaction, then rechecks cleared state before reporting completion for that exact child and attempt. Hiding metadata or observing elapsed time is not proof of reset. Missing confirmation fails even when no ticket is visible; the child remains available for inspection. Preserve the CLI-initialized name and leave the original session unchanged. Defer reset waiting and interaction/MCP initialization so Hub's startup handler cannot prevent later producer handlers from running. The separate Hub-owned `theme-command.json` is a deliberately narrow one-time control bridge: parent extensions compare its timestamp/revision to process start, resolve the concrete global theme through Pi, apply a `Theme` object without rewriting settings, and heartbeat immediately; subagents and older commands are ignored. The workflow producer owns each ordered `WorkflowSnapshot.steps` definition, state-change timestamp, optional active-mode display, and optional `currentStepComplete` boolean. Hub validates the base workflow and each decoration independently but mirrors no step ids, short codes, labels, mode vocabulary, or legacy fallback; invalid decoration does not hide a valid base workflow. One pure positional marker rule serves project rows, board cards, and the action workspace: indexes before `activeIndex` are complete; the current index is complete only when `currentStepComplete === true`, otherwise active; later indexes are pending. Direct later-step invocation therefore checks earlier positions. This is a position cue rather than sequence enforcement or an execution audit. Completion does not change lane placement, and retained terminal snapshots remain visible across stale/shutdown state until a new workflow snapshot replaces them. Base workflow state may be retained in `registry.json`, but `SessionsController` merges a mode only into `RuntimeSession` from a fresh non-shutdown heartbeat with confirmed tmux presence, so modes never affect persistence or liveness.
- Managed-session lifecycle orchestration lives in `src/app/session-lifecycle.ts`; it owns add/start/stop/restart/fork, delete, subagent cleanup, and worktree finish/discard sequencing while reusing core adapters. Normal fork and Fork and compact share the same group-selection form; the compact variant adds only the one-shot startup behavior described above. `src/app/delete-session.ts` and `src/app/worktree-session.ts` remain explicit safety entry modules for delete and Git lifecycle flows and delegate to the central module; callers must keep using those entry paths. Normal delete stops tmux, removes any owned multi-repo workspace, removes the registry row, removes the heartbeat, and keeps Pi conversation/session files. Normal delete intentionally keeps hub-owned worktree directories. Finish or discard performs a clean-state preflight, records stage-aware per-repository evidence, and after Git reloads and stops the latest exact cascade. Verified success retains the same parent as stopped and Archived with source-root cwd values and merged/discarded cleanup history; it removes obsolete children, workspaces, and heartbeats. Partial failure keeps completed stage evidence and unresolved mappings. Multi-repo worktree finish/discard handles additional repos before the primary repo so partial failures keep the primary session cwd recoverable. Tmux, workspace, and Git work that determines a lifecycle mutation stays outside the lock and completes before the short registry update; after the registry commit, remove each session's heartbeat. `removeSessions(sessions, path, env)` filters only prepared IDs from the latest registry after tmux/workspace cleanup. Successful deletion removes only the prepared IDs from latest state, while partial worktree failure transforms the latest surviving parent after failed external work.
