# pi-agent-hub Structure

`pi-agent-hub` is a minimal TypeScript package for managing Pi coding-agent sessions in tmux. It is Pi-only: Pi remains the agent runtime, tmux remains the process substrate, and this package supplies the dashboard/registry glue.

## Layout

```text
src/
  cli.ts                 command entrypoint (`pi-hub`; `pi-agent-hub` remains an alias)
  index.ts               public exports
  app/                   dashboard launcher, controller, refresh loop, and shared session actions for the standalone TUI
  core/                  shared JSON store/locking, registry, paths, tmux, Pi process args, status reducer, multi-repo workspace and worktree helpers
  extension/             tiny Pi extension for session heartbeats
  mcp/                   MCP catalog/project config, direct clients, pool, tool adapter
  skills/                project skill attach/detach and pool discovery
  tui/                   pure render model, terminal layout, dialog modules, shared text/form primitives, picker, and theme helpers
test/                    Node test-runner tests compiled by TypeScript
package.json             npm package metadata, SemVer version, CLI bins, and Pi extension declaration
CHANGELOG.md             npm/GitHub release notes, maintained per published version
docs/STRUCTURE.md        this developer onboarding guide
docs/FEATURES.md         user-facing feature map and dashboard workflow
docs/CONFIG.md           runtime state, global config, themes, Skills/MCP setup
docs/DEVELOPMENT.md      local setup, tests, package checks, smoke testing, release workflow
docs/history/             archived feature notes; useful context, not current product contracts
```

## Runtime state

- Global state lives under `PI_AGENT_HUB_DIR` or `<PI_CODING_AGENT_DIR>/pi-agent-hub`.
- Optional global config lives at `config.json`; it can set skill pool directories, the MCP catalog path, a managed-session `session.prelude` shell snippet, and `session.worktreeDefault` for new-session forms.
- The session registry is `registry.json`.
- The last observed tmux server epoch is `tmux-server.json`; it stores the server pid, start time, and socket path used to detect whole-server replacement.
- `pi-hub` opens a stable dashboard tmux session named `pi-agent-hub`; use `pi-hub tui` to run the TUI directly without the dashboard wrapper. The `pi-agent-hub` command remains available as a compatibility alias.
- Managed Pi sessions write heartbeat files under `heartbeats/<session-id>.json` through the extension. Extensions can also write optional semantic metadata to `session-metadata/<session-id>.json`; Hub can display this file's known fields, but it never affects process liveness.
- Optional `pi-tmux-subagents` compatibility uses flat registry rows with `kind: "subagent"`, `parentId`, `agentName`, `taskPreview`, and `resultPath`; the dashboard renders those rows nested under their parent with a short agent-name row label, while task preview belongs in details/filtering. Standalone subagent state remains owned by `pi-tmux-subagents`, and dashboard refresh prunes subagent rows whose tmux sessions are gone so stale completed rows do not linger.
- Managed tmux sessions use the `pi-agent-hub-<first-12-session-id-chars>` name. If `session.prelude` is configured, it runs inside the managed tmux shell before `exec pi`; dashboard launch and direct `pi-hub tui` do not run it.
- Multi-repo sessions keep `ManagedSession.cwd` as the primary repo and start Pi from `<global-state>/workspaces/<session-id>`, a symlink workspace containing the primary repo, each additional repo, and `.pi -> <primary>/.pi`. If selected repo roots contain `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, or `CLAUDE.MD`, Hub generates a workspace-root `AGENTS.md` that labels and embeds those repo instructions so Pi loads them from the workspace cwd.
- Hub-owned worktree sessions keep `ManagedSession.cwd` as the primary worktree path and store metadata in the registry. New rows use `worktrees[]` with one entry per repo (`path`, source `repoRoot`, branch, base branch, role), while scalar `worktreePath`/repo/branch fields remain compatibility metadata. Worktrees live under `<global-state>/worktrees/<repo-name>/<session-id-prefix>-<branch-slug>`.
- Recent repo choices for the new-session picker live in `<global-state>/repo-history.json`; current registry paths are merged with this bounded history at TUI startup.
- Project skill state lives in `<project>/.pi/sessions/skills.json`; available skills come from `skills.poolDirs` in global config or `<global-state>/skills/pool`.
- Project MCP enablement lives in `<project>/.pi/sessions/mcp.json`; available MCP servers come from the configured catalog path or `<global-state>/mcp.json`.
- JSON state files use `src/core/atomic-json.ts` for atomic writes, optional version/shape parsing, shared errno checks, and lock-dir guarded read-modify-write updates.
- In the standalone TUI, `<project>` for Skills/MCP pickers is the selected session's primary cwd, with dashboard cwd as the fallback when nothing is selected. For multi-repo sessions, Skills/MCP state applies to the primary repo only.
- Pooled MCP uses a Unix socket at `<global-state>/pool/pool.sock`; run `pi-hub mcp-pool` explicitly when pooled servers are enabled.
- Inside-tmux switch return state lives under `return-key/` while a temporary `Ctrl+Q` binding is active; `pi-hub doctor` reports active/stale return state.

## Build and test

```bash
npm install
npm test
npm run build
node dist/cli.js --help

```

## Design rules

- Keep public names centralized in `src/core/names.ts`; `pi-hub` is the primary CLI command, `pi-agent-hub` is a compatibility alias, and runtime state/tmux names remain `pi-agent-hub`. CLI install diagnostics live in `src/core/install-diagnostics.ts`: they may warn and report exact PATH fixes, but must not mutate PATH, shell profiles, npm globals, or Pi package directories.
- Keep status logic centralized in `src/core/status.ts`. The TUI acknowledges a `waiting` session before attach/switch so opening it clears the unread/waiting indicator; keep that ordering when changing attach behavior. Fresh managed-session heartbeats can also carry the active Pi theme snapshot used by the dashboard and tmux chrome; stale or shutdown heartbeats must clear it so disk settings remain the fallback. The heartbeat `workflow` snapshot (bridged from the optional workflow-runtime extension; see CONFIG.md) is the deliberate contrast: it is state about the work, not live chrome, so `applyComputedStatus` adopts it from fresh heartbeats but retains the last known value across stale/shutdown heartbeats — a stopped session keeps its stage lane. The latest heartbeat `stateSince` is retained as `lastActivityAt`.
- Keep tmux shelling centralized in `src/core/tmux.ts`. The default dashboard launcher creates/attaches/switches to `pi-agent-hub`; direct TUI mode is `pi-hub tui`. Dashboard tmux creation must run `tui` through the current CLI file via `cliTuiCommand` in `src/core/tmux.ts`, not bare `pi-hub tui`, so a Pi-installed entrypoint does not recurse into a stale global command on PATH. Inside-tmux managed-session attach uses native `switch-client` plus temporary guarded root bindings: `Ctrl+Q` returns to the dashboard, and `Alt+R` writes a dashboard action then returns into the selected session's rename dialog and switches back after a successful rename. No-prefix root bindings are tmux-server-global, so dashboard-only shortcuts must forward the original key sequence outside the dashboard rather than merely making the guarded action a no-op, and temporary binding sets must restore prior root bindings on cleanup. Return binding scripts can recreate the dashboard before returning and only restore previous bindings after a successful return switch; dashboard recreation must preserve `PI_CODING_AGENT_DIR`/`PI_AGENT_HUB_DIR` via `dashboardEnv()`. Outside-tmux direct TUI attach remains normal `tmux attach-session`. Dashboard and managed-session tmux chrome is configured there too: both override status/window styles and formats so global tmux themes do not leak in, derive colors from `src/core/chrome.ts` theme tokens when available, sync active managed status bars from the dashboard on load/theme changes, and keep managed status-right as `ctrl+q return · alt+r rename │ 📁 <session title> | <project>`.
- Keep server-loss recovery in `src/app/session-recovery.ts`. Automatic recovery is gated by a changed tmux server epoch, then starts only missing Active parent rows that were not explicitly stopped; manual `pi-hub recover` uses the same target and validation rules without requiring an epoch change. Validate primary/additional cwd paths and saved Pi history before start, recover sequentially, and isolate failures so one bad row cannot block the rest. Never auto-start Backlog, Archived, stopped, or subagent rows, and never treat a single missing session on an unchanged server as a whole-server restart.
- The sidebar workspace is nested tmux attach inside the TUI's own window, not a new session model. `src/app/side-pane.ts` inspects panes live through `src/core/tmux.ts`, treats only non-dashboard panes whose tty maps to a `pi-agent-hub-*` client as Hub-owned content panes, and never persists panel state in the registry. Slots are fixed quadrants (`1` top-left, `2` top-right, `3` bottom-left, `4` bottom-right) tagged on live panes with `@pi_hub_slot`; inspection repairs missing or duplicate tags into the lowest free slots in geometry order. Layout is derived from occupancy, permits holes, and expands degenerate shapes rather than reserving blank regions. Bare `1`–`4` keys assign, replace, move, swap, or focus but never close; `x` then `1`–`4` closes explicitly, `F` then `1`–`4` focuses from the TUI, and guarded `Alt+1`–`Alt+4` root bindings resolve and focus tagged panes at keypress time from anywhere in the dashboard session. `Alt+Q` returns from a panel to the sidebar, with `Ctrl+Q` retained as a fallback, while `o` rebuilds one selected panel or closes it when already alone. Successful assignment focuses the landed pane; explicit close, narrow-width refusal, and `o` reset remain sidebar-focused. To avoid visible Pi conversation reflow, rebuilds pre-size each managed session window off-screen, create panes at their exact final dimensions, tag and title each pane, and restore every target to `window-size latest` only after the final split. Full-screen switching follows the same pre-size/switch/restore sequence; reset failures must remain observable, and a failed post-switch reset must not remove the active return binding. Live inspection supplies numbered `◫1`–`◫4` row indicators, a sparse four-slot sidebar strip built from the full unfiltered session list, matching pane titles, and the active quadrant. Theme-derived window-local pane options keep the focused border and reverse-color title badge accented while inactive borders/titles stay muted; opening and theme changes reapply them, while teardown unsets them. Single-click selects a row, double-click performs the full-screen `Enter` action, and wheel input moves selection. Mouse input is dashboard-session scoped: enable tmux `mouse` only on `pi-agent-hub`, request SGR button reporting from the TUI pty, and unset the session override on quit. Serialize presence inspection, panel mutation, focus, and full-screen handoff through the side-pane operation queue; stop and drain polling before a full-screen switch. When managed panes exist, hide the outer dashboard status bar, hide each paneled managed session's session-scoped status footer, enable top pane borders, suppress the sidebar's built-in details/preview column, and install the guarded return/focus binding set. Restore each managed footer before full-session handoff and when its panel closes or the dashboard shuts down; restore the dashboard chrome and built-in preview when no panels remain. The presence loop keeps the sidebar between 40 and 60 columns while managed panes exist: collapsed panes return to the 42-column default, oversized panes shrink to 60 columns (or less when needed to retain 40 content columns), and widths within that range remain user-controlled. Do not use tmux hooks or `select-layout`, which fight manual arrangements. Full-screen switching closes only the pane showing that target session; dashboard quit closes all Hub-owned side panes before stopping the TUI. Do not target tmux window/pane indexes; use `$TMUX_PANE`, `#{pane_id}`, pane ttys, and `switch-client -c <tty>`.
- Keep extension loading idempotent. Managed sessions still pass `--extension` so linked CLI usage works without `pi install`; when the package is also installed, the extension may load twice in one Pi process. Suppress duplicate registration, but clear active process guards on `session_shutdown` so later sessions can register. The extension heartbeat is the generic bridge for live Pi session state such as active theme and workflow stage; avoid package-specific theme-sync integrations. The workflow-runtime entry format and step list are mirrored only in `WORKFLOW_STEPS` in `src/extension/index.ts`; the render layer stays generic over `WorkflowSnapshot.steps` and never hardcodes step names.
- Delete sessions through `src/app/delete-session.ts`: stop tmux, remove any owned multi-repo workspace, remove the registry row, remove the heartbeat, and keep Pi conversation/session files. Normal delete intentionally keeps hub-owned worktree directories; finish or discard worktree sessions through `src/app/worktree-session.ts`, which stops the session/subagent tmux processes after a clean-state preflight, then merges/removes or discards all session worktrees before removing registry rows and heartbeats. Multi-repo worktree finish/discard handles additional repos before the primary repo so partial failures keep the primary session cwd recoverable. Archive pruning is separate and dashboard-only after seven days: `src/app/controller.ts` removes expired archived registry rows plus heartbeat, session-metadata, and owned multi-repo workspace state only after every row in the session/subagent cascade is confirmed missing from tmux. The TUI pauses the refresh loop before deletion/finish/discard mutations so stale snapshots cannot rewrite deleted rows.
- Groups are implicit flat labels on sessions, not separate records. Creating a session with a new group label creates the group; pressing `g` in the TUI moves the selected session to an existing or new group, while `G` renames the selected session's current group for all sessions in that group. Pressing `K`/`J` or Shift-Up/Shift-Down reorders the selected Active or Backlog session within its current group; Archived is globally chronological and cannot be manually reordered. Pressing `A`, `B`, or `U` archives, backlogs, or restores a parent session by updating optional `ManagedSession.bucket` / `bucketChangedAt` fields; these actions never stop tmux/Pi, and subagent rows inherit their top-level parent's effective lifecycle instead of moving directly. Archived shows the five newest parent cascades by default and exposes older cascades through an ephemeral disclosure target. Pressing `R` renames the selected session title in the dashboard footer; `N` syncs the selected hub title from the latest Pi `session_info` name in its saved session file. In-session `Alt+R` keeps the explicit dashboard rename dialog because that flow temporarily leaves the managed session before switching back. Pressing `p` sends a one-line footer prompt to the selected live session through tmux paste without opening it. Pressing `Enter` on a stopped or error row restarts it instead of attempting to attach. Pressing `r` opens restart choices: `r` resumes the selected saved Pi conversation, `n` clears the selected hub row's Pi session metadata and starts a new Pi conversation in the same tmux/session record, and `a` restarts all active non-subagent sessions while skipping Backlog and Archived. Do not add separate empty-group lifecycle unless the model changes.
- Active and Backlog project groups and rows use the same ordering tiers: errors first, starting/running next, waiting and idle mixed by newest `lastActivityAt`, and stopped last. Groups in the waiting/idle tier are ordered by their newest member activity, then by existing group order. `ManagedSession.order` is optional registry data, breaks exact priority/activity ties, and falls back to group-relative registry order; new/forked/group-moved sessions append to the target group within the current lifecycle section. `K`/`J` reorder only inside the selected row's current tie. `src/core/session-order.ts` owns this ordering while keeping Archived globally newest-first by archive time; all-active dashboards suppress section headers in the render layer. Controller navigation and render grouping must use `src/core/session-tree.ts`, which builds on `src/core/session-order.ts` and nests optional subagent rows recursively under parents. Titles never affect order, and stopped sessions remain in the group instead of rendering in a separate subsection.
- `SessionsController` clears cached preview output and request-guards captures when selection changes so late results cannot paint an older session. Interactive selection paths in `src/app/run-tui.ts` trigger capture immediately; the periodic refresh loop remains responsible for live updates.
- Keep rendering pure and testable in `src/tui/*`; ANSI styling must stay width-safe via theme helpers. In groups view, Active and Backlog rows use fixed slots for a muted workflow stage and right-aligned activity age, with the age blank while running; Archived rows remain age-only. Dashboard rendering must be safe at any pane size: `SessionsView.render()` owns the below-40-col narrow notice, `renderSessions()` bounds output to terminal height, and mouse hit maps must describe only visible rows. The `v` stage-lane view reuses the lifecycle-section rendering machinery (`RenderSection` with string lane keys via `stageLaneRows`) instead of a separate layout path: lanes show active-lifecycle rows only, subagents inherit their parent's lane, reordering is groups-view only, and `v` is reserved from custom dashboard shortcuts. The Archived disclosure is a synthetic non-session render target so session actions cannot reach a stale real selection; archive ages and pruning eligibility are computed from each row's effective top-level parent lifecycle. The selected row uses an accent `▌` edge plus the `selectedBg` background token applied after column padding so the bar spans the list column; footer strings stay plain in the render model and are styled in `layout.ts`. At sidebar width, show a small labeled set of primary controls plus `? Help` rather than an unlabeled list of keys. The dashboard theme uses the last-entered session as its anchor when present, falls back to the initially selected session, and resolves that anchor through fresh heartbeat theme snapshots before Pi settings in `src/tui/theme.ts` and the small refresh loop in `src/app/run-tui.ts`; tmux chrome uses the same loaded `SessionsTheme` structurally through `src/core/chrome.ts` while keeping tmux option writes outside pure render code. Contextual selected-session capability hints should stay quiet and data-backed: multi-repo count comes from the session row, MCP count from `enabledMcpServers`, and Skills count from the cached project Skills state loaded by `src/app/run-tui.ts`.
- Use `src/tui/text-input.ts` for cursor-aware single-line editing across all TUI text inputs, including forms, slash filter, dashboard footer prompts, and picker search. Route session dialog state through the `SessionDialog` union in `src/tui/dialog.ts` and keep per-family behavior in the small `*-dialog.ts` modules. Use `src/tui/form.ts` plus `renderForm()` for editable dialogs. Keep `src/tui/new-form.ts` limited to new-session defaults, cwd suggestions, worktree-mode branch/title submission, and validation; reserve `renderDialog()` for non-editable confirmations. Editable dialogs should show the same visible affordances as the new-session form: focused-field marker, cursor, hint text, and concise footer. Use `src/tui/repo-picker.ts` for focused repo selection; do not add filesystem scanning or async project discovery to populate choices. Use `▶` sparingly as the primary-action cue in confirmations, empty states, and no-match states.
- Use `src/core/atomic-json.ts` for JSON persistence: `loadStore` for missing-file defaults plus version/shape parsing, `updateStore` for locked read-modify-write updates, `writeJsonAtomic` for direct snapshot writes, and `isErrno` for filesystem errno checks.
- Use single bulk writes for multi-item project state changes; avoid parallel read-modify-write loops against JSON files.
- Keep clipboard integration best-effort. The UI must always show the actionable tmux command even when clipboard tooling is missing.
- Prefer small functions and explicit data shapes over framework abstractions.
