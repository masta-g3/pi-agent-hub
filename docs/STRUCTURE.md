# pi-agent-hub Structure

`pi-agent-hub` is a minimal TypeScript package for managing Pi coding-agent sessions in tmux. It is Pi-only: Pi remains the agent runtime, tmux remains the process substrate, and this package supplies the dashboard/registry glue.

## Layout

```text
src/
  cli.ts                 command entrypoint (`pi-hub`; `pi-agent-hub` remains an alias)
  index.ts               public exports
  app/                   dashboard launcher, controller, refresh loop, and shared session actions for the standalone TUI
  core/                  shared heartbeat intake, JSON store/locking, registry, paths, tmux, Pi process args, status reducer, multi-repo workspace and worktree helpers
  extension/             tiny Pi extension for session heartbeats
  mcp/                   MCP catalog/project config, direct clients, pool, tool adapter
  skills/                project skill attach/detach and pool discovery
  tui/                   pure render model, terminal layout, dialog modules, shared text/form primitives, picker, and theme helpers
test/                    Node test-runner tests compiled by TypeScript
package.json             npm package metadata, SemVer version, CLI bins, and Pi extension declaration
CHANGELOG.md             npm/GitHub release notes, maintained per published version
docs/STRUCTURE.md        this developer onboarding guide
docs/FEATURES.md         user-facing feature map and dashboard workflow
docs/CONFIG.md           runtime state, global config, themes, Skills/MCP setup
docs/DEVELOPMENT.md      local setup, tests, package checks, smoke testing, release workflow
docs/history/             archived feature notes; useful context, not current product contracts
```

## Runtime state

- Global state lives under `PI_AGENT_HUB_DIR` or `<PI_CODING_AGENT_DIR>/pi-agent-hub`.
- Optional global config lives at `config.json`; it can set skill pool directories, the MCP catalog path, a managed-session `session.prelude` shell snippet, and `session.worktreeDefault` for new-session forms.
- The session registry is `registry.json`; `ui-state.json` persists project/board grouping, the normalized dashboard filter (text plus an ordered lifecycle array), HEALTH/ACTIVE/QUIET/ARCHIVED cockpit collapse preferences, the bounded first-run onboarding phase, and one dismissed release-cue ID. `NEEDS YOU` is never persisted as collapsed. A missing state file plus an empty initial registry creates and immediately writes the new-user cohort; a missing file with a nonempty registry remains an existing-user state. Malformed or unsupported saved fields are ignored while valid fields survive. Card richness, responsive widths, tree disclosure, tier navigation, and filtered reveals remain ephemeral.
- `pi-hub` opens a stable dashboard tmux session named `pi-agent-hub`; use `pi-hub tui` to run the TUI directly without the dashboard wrapper. The `pi-agent-hub` command remains available as a compatibility alias.
- Managed Pi sessions write heartbeat files under `heartbeats/<session-id>.json` through the extension. `src/core/heartbeat.ts` reads each file as unknown data, requires a valid liveness envelope and a `managedSessionId` matching the requested file, then normalizes optional identity, theme, context, and workflow data before dashboard use. A malformed envelope is treated as a missing heartbeat; malformed optional metadata is omitted without hiding valid liveness. Unknown producer fields remain compatible. Each valid heartbeat can include Pi's native session name, the latest valid producer-neutral `pi-agent-hub-context` snapshot, and optional producer-owned workflow runtime. The registry title starts as the primary repo basename and becomes a cache of nonblank heartbeat names. Generic subtitle, description, and attention remain runtime-only. Workflow activity and deterministic plan progress travel inside `workflow-runtime`; Hub does not read producer files or a metadata sidecar.
- Optional `pi-tmux-subagents` compatibility uses flat registry rows with `kind: "subagent"`, `parentId`, `agentName`, `taskPreview`, and `resultPath`; the dashboard renders those rows as nested micro rows with bounded agent name and task preview; the same task preview remains available to the action workspace and filtering. Standalone subagent state remains owned by `pi-tmux-subagents`, and dashboard refresh prunes subagent rows whose tmux sessions are gone so stale completed rows do not linger.
- Managed tmux sessions use the `pi-agent-hub-<first-12-session-id-chars>` name. If `session.prelude` is configured, it runs inside the managed tmux shell before `exec pi`; dashboard launch and direct `pi-hub tui` do not run it.
- Multi-repo sessions keep `ManagedSession.cwd` as the primary repo and start Pi from `<global-state>/workspaces/<session-id>`, a symlink workspace containing the primary repo, each additional repo, and `.pi -> <primary>/.pi`. Every managed parent launch, including the direct normal-session fork path, exports `PI_AGENT_HUB_PRIMARY_CWD=ManagedSession.cwd`; it never exports `workspaceCwd` or an additional repo through that variable. This gives producer extensions one optional process-local project root when resumed conversation history retains a different Pi header cwd, without persisting the path or changing normal `f`/worktree behavior. If selected repo roots contain `AGENTS.md`, `AGENTS.MD`, `CLAUDE.md`, or `CLAUDE.MD`, Hub generates a workspace-root `AGENTS.md` that labels and embeds those repo instructions so Pi loads them from the workspace cwd.
- Hub-owned worktree sessions keep `ManagedSession.cwd` as the primary worktree path and store metadata in the registry. New rows use `worktrees[]` with one entry per repo (`path`, source `repoRoot`, branch, base branch, role), while scalar `worktreePath`/repo/branch fields remain compatibility metadata. Worktrees live under `<global-state>/worktrees/<repo-name>/<session-id-prefix>-<branch-slug>`. At process start, `src/core/worktree-context.ts` validates the complete mapping and supplies one bounded guidance string to the Hub extension and the optional `pi-tmux-subagents` prompt bridge. The extension appends that guidance to each parent turn through `before_agent_start`; child launchers receive the same text through their package-owned boundary instead of loading Hub state.
- Recent repo choices for the new-session picker live in `<global-state>/repo-history.json`; current registry paths are merged with this bounded history at TUI startup.
- Project skill state lives in `<project>/.pi/sessions/skills.json`; available skills come from `skills.poolDirs` in global config or `<global-state>/skills/pool`.
- Project MCP enablement lives in `<project>/.pi/sessions/mcp.json`; available MCP servers come from the configured catalog path or `<global-state>/mcp.json`.
- JSON state files use `src/core/atomic-json.ts` for atomic writes, optional version/shape parsing, shared errno checks, and lock-dir guarded read-modify-write updates. `src/core/registry.ts` owns registry freshness: `loadRegistry()` reads state, while `updateRegistry()` is the sole registry write path. Registry updates compare their persisted JSON snapshot inside the lock and skip the atomic write when it is unchanged; other JSON stores retain their configured write behavior.
- In the standalone TUI, `<project>` for Skills/MCP pickers is the selected session's primary cwd, with dashboard cwd as the fallback when nothing is selected. For multi-repo sessions, Skills/MCP state applies to the primary repo only.
- Pooled MCP uses a Unix socket at `<global-state>/pool/pool.sock`; run `pi-hub mcp-pool` explicitly when pooled servers are enabled.
- Inside-tmux switch return state lives under `return-key/` while the temporary `Ctrl+Q` binding is active; `Alt+Q` remains available to Pi for message editing. `pi-hub doctor` reports active/stale return state.

## Design rules

- Keep public names centralized in `src/core/names.ts`; `pi-hub` is the primary CLI command, `pi-agent-hub` is a compatibility alias, and runtime state/tmux names remain `pi-agent-hub`. CLI install diagnostics live in `src/core/install-diagnostics.ts`: they may warn and report exact PATH fixes, but must not mutate PATH, shell profiles, npm globals, or Pi package directories.
- Keep heartbeat shape and identity checks centralized in `src/core/heartbeat.ts`. Producer `workflow-runtime` entries identify position with `activeStep`, while persisted heartbeat workflows use `activeIndex`; separate adapters share step and decoration checks and must not accept the other position shape. The extension owns publication timing and atomic serialized writes. Keep liveness reduction and retention centralized in `src/core/status.ts`, and keep registry/runtime projection in `src/app/controller.ts`; neither layer reparses heartbeat metadata. The TUI acknowledges a `waiting` session before attach/switch so opening it clears the unread/waiting indicator; keep that ordering when changing attach behavior. Pi's coalesced `ui_prompt_start` / `ui_prompt_end` span temporarily publishes `waiting` and restores the prior state only while a monotonic lifecycle revision still belongs to that prompt; newer same-state or different-state lifecycle events invalidate restoration. Fresh managed-session heartbeats can also carry the active Pi theme snapshot used by that session's managed tmux chrome; stale or shutdown heartbeats must clear it so disk settings remain the per-session fallback. Dashboard theming is independent: synchronized mode reads Pi's global theme setting, detached mode reads Hub's override, and neither follows a heartbeat/session anchor. The heartbeat `workflow` snapshot (bridged from the optional workflow-runtime extension; see CONFIG.md) is the deliberate contrast: it is state about the work, not live chrome, so `applyComputedStatus` adopts it from fresh heartbeats but retains the last known value across stale/shutdown heartbeats — a stopped-but-Active session remains eligible for its board lane. The latest heartbeat `stateSince` is retained as `lastActivityAt`; compaction heartbeats use the pre-compaction `stateSince` so transient green compaction activity does not make an old session newly recent. `workflow.updatedAt` is the producer's state-change timestamp and may advance within one step, while heartbeat `updatedAt` remains the independent liveness timestamp.
- Keep tmux shelling centralized in `src/core/tmux.ts`. The default dashboard launcher creates/attaches/switches to `pi-agent-hub`; direct TUI mode is `pi-hub tui`. Dashboard tmux creation must run `tui` through the current CLI file via `cliTuiCommand` in `src/core/tmux.ts`, not bare `pi-hub tui`, so a Pi-installed entrypoint does not recurse into a stale global command on PATH. Inside-tmux managed-session attach uses native `switch-client` plus a temporary guarded `Ctrl+Q` root binding to return to the dashboard; `Alt+Q` is never intercepted because Pi uses it to edit the last message. `Alt+R` writes a dashboard action then returns into the selected session's rename dialog and switches back after a successful rename. No-prefix root bindings are tmux-server-global, so dashboard-only shortcuts must forward the original key sequence outside the dashboard rather than merely making the guarded action a no-op, and temporary binding sets must restore prior root bindings on cleanup. Return binding scripts can recreate the dashboard before returning and only restore previous bindings after a successful return switch; dashboard recreation must preserve `PI_CODING_AGENT_DIR`/`PI_AGENT_HUB_DIR` via `dashboardEnv()`. Outside-tmux direct TUI attach remains normal `tmux attach-session`. Dashboard and managed-session tmux chrome is configured there too: both override status/window styles and formats so global tmux themes do not leak in, derive colors from `src/core/chrome.ts` theme tokens when available, sync active managed status bars from the dashboard on load/theme changes, and keep managed status-right as `ctrl+q return · alt+r rename │ 📁 <session title> | <project>`.
- `SessionsController.refresh()` obtains one `tmux list-sessions -F '#{session_name}'` snapshot per refresh. `src/core/tmux.ts` reduces listed names to present/missing/unknown observations, retains unknown errors for status reduction, and prunes only explicit missing subagent/archive cascades. `createSessionTreeIndex()` supplies cached queue-based descendants for cascade work; callers still preserve raw, filtered, active, projected, and lane-local scope distinctions.
- Status explanations stay attached to their decision sources. `computeStatus()` emits structured runtime evidence from the reducer branch it takes, and the cockpit index emits placement evidence from the branch that assigns the owner tree's tier; the first active row in cached descendant order is the deterministic activity driver. `src/app/session-observation.ts` owns the shared read-only fleet observation used by controller refresh and `pi-hub explain`, including one bulk tmux snapshot and validated heartbeat reads. `SessionsController` exposes evidence only when its fingerprint still matches the row's tmux target, status, error, acknowledgement, and workflow; title, group, and order changes do not invalidate it. Missing evidence triggers the existing serialized refresh path before the workspace reveals evidence. The CLI observes the complete fleet once so owner/descendant placement matches the dashboard, but it never calls `updateRegistry()`. `src/tui/status-evidence.ts` is the single semantic wording builder for themed TUI and plain CLI output. `i` appends or hides useful evidence inside the selected-session action workspace. At 120+ columns that workspace is persistent; below 120 it is an ephemeral session-ID-bound full-width screen. Selection repair closes stale full-width state, and every rendered workspace action carries an exact catalog command ID. Workflow provenance remains a separate evidence fact and never becomes liveness or placement evidence.
- `src/tui/render-model.ts` owns the pure structural dashboard projection shared by rendering and `SessionsView` navigation. The view may reuse that projection for one registry/view-state snapshot, but volatile values such as current time, side-pane slots, and selection overlays are applied per render. Dialog modules receive family-specific narrowed action contexts; the flat action bag remains only at the composition boundary for compatibility. `renderForm()`, `renderDialog()`, and dashboard `box()` share a width-safe frame helper without changing their visual tokens.
- `src/tui/cockpit-onboarding.ts` owns bounded normalization and pure transitions for the persisted first-run cohort, exact explicit-request trip, completion, and versioned release-cue dismissal. `src/app/run-tui.ts` classifies a new user only when `ui-state.json` is missing and the initial registry is empty; all other users receive only the current release cue. `SessionsView` starts the trip only after exact question acknowledgement plus successful pin focus or full-screen handoff, and completes it only after canonical `Ctrl+Q` returns successfully. Sidebar return completes directly; full-screen return writes a typed `{ action: "return", key: "ctrl-q" }` dashboard-action receipt after `tmux switch-client` succeeds. Locate, manual acknowledgement, failed routing, and attention without a request ID do not advance it. Coaching and the synthetic release row are presentation-only, suppressed outside normal unfiltered project mode, and never enter fleet counts or session actions. UI-state writes serialize complete snapshots. Shutdown first drains active side-pane and dashboard-action producers, then drains the UI-state writer, so a late transition or stale write cannot overwrite completion or dismissal.
- `src/tui/dashboard-commands.ts` is the shared pure catalog for catalog-owned direct keys, the `:` intent palette, dashboard Help, configured shortcuts, selected-workspace rows, and stable footer controls. Its fixed presentation order is selected-target actions, configured actions, sessions, named filters, then views/Help. Command descriptors carry stable namespaced IDs, every retained binding alias, search text, capability-dependent availability, and concise disabled reasons. Selected-target and configured-command IDs include the exact session identity; `SessionsView` rebuilds and revalidates that identity before execution, and forms/pickers retain the bound session/project through submission instead of consulting later selection. Disabled commands are discoverable but inert regardless of whether direct keys or the palette invoked them. Session search composes the bounded `matchesFilter()` fields and follows the unfiltered cockpit projection before appending hidden rows; it never searches pane output or Pi conversations. Session-result activation only selects and ephemerally reveals the exact current row, clears a fleet filter only when needed, and never attaches, restarts, or acknowledges. The ephemeral reveal can expose one collapsed/older Archived cascade or leave stage grouping for project grouping without persisting disclosure/grouping state, and clears on later navigation or view changes. Keep modal, text-editing, busy, full-width-workspace, pending-choice, tree-disclosure, and mouse precedence above normal command dispatch. Future action surfaces must consume the catalog instead of adding a parallel command table.
- `src/app/attention-delivery.ts` owns the pure process-local transition from validated producer attention to transient delivery. Producers supply optional bounded request IDs; Hub seeds current identities silently at startup, deduplicates by session plus request ID, persists no delivery history, and expires each active entry after six seconds. `src/app/run-tui.ts` owns best-effort effects after successful refresh: only the managed dashboard tmux session can inspect clients, send literal-safe six-second messages, or emit the opt-in BEL. Per-client routing suppresses the exact cockpit pane, managed session, or requesting pin; any suppressed client disables the process-wide BEL without blocking text to other eligible clients. `SessionsView` receives bounded active presentation data, revalidates the exact request before locate or acknowledgement, and keeps global locate/bell commands independent from synthetic or missing selected-row targets. Rendering and tmux adapters sanitize producer text through `src/core/terminal-text.ts`; neither layer detects transitions or persists state.
- The sidebar workspace is a set of nested tmux attaches inside the dashboard window, not a second session model. `src/app/side-pane-lifecycle.ts` is the sole serialized boundary for presence, assignment, focus, resize, handoff, chrome, and shutdown; `src/app/side-pane.ts` owns stateless inspection, topology, repair, rollback, and pane mutation through `src/core/tmux.ts`. Canonical state is one sparse four-slot projection. `@pi_hub_slot` is transient pane metadata only; every operation also validates pane ID plus tty-to-`pi-agent-hub-*` managed identity, repairs missing/duplicate tags deterministically, reconciles duplicate attaches, and ignores user panes. Bare `1`–`4` assigns the exact selected live session to a free slot, `P` chooses the lowest free slot or focuses its existing slot, `x` closes that selected identity, and occupied destinations refuse without retarget, swap, replacement, acknowledgement, or eviction. Guarded `Alt+1`–`Alt+4` focuses slots from anywhere in the dashboard session; guarded `Alt+Arrow` remains optional spatial focus, and only `Ctrl+Q` returns to the cockpit. `Alt+Q` remains available to Pi for message editing. Root bindings target the saved sidebar pane with an intent, pass the original key outside the dashboard, and restore prior server-global bindings. Whole-window capacity is zero below 100 columns, slots 1–2 at 100–159, and slots 1–4 at 160+. Width contraction preserves every existing slot, marks the layout constrained, and blocks additions/resizing while still allowing safe close and rollback. Slots 1–2 stack below 120 and sit side by side at 120–159; full-slot topology uses columns `1/3` and `2/4`, expands holes, and keeps 1/3 or 2/4 resizing on the vertical axis. `+`/`-` changes the topology's main split in ten-point steps clamped to 30/70. Rebuilds pre-size every target at final geometry, split at final size, tag/title the pane, and restore `window-size latest`; only confirmed vanished targets are ignored, while other preparation errors enter rollback and prior attachments are restored before the error surfaces when possible. Pin creation keeps cockpit focus and does not acknowledge; explicit pin/slot/spatial focus and full-screen handoff reveal the exact row and acknowledge waiting state before focus. Question Answer routing uses a serialized exact-session focus operation: it re-inspects live pins by tmux target, then reveals, acknowledges, and focuses that target, or returns unavailable so SessionsView can use normal full-screen attach. It never carries a stale slot number across the operation. Rendering derives only from the sparse slot projection: rows use `▢N`/`▣N`, the bounded `PINNED` summary includes available holes, pane titles use `LIVE N · <title>` with optional owner/ticket context, and the narrow cockpit keeps the decision/evidence strip. Restore the target managed footer when its pin closes or before its full-screen handoff. Keep shared dashboard status, pane-border chrome, and pin bindings active while any pin remains; restore them after the final close or during shutdown. Keep the sidebar between 40 and 60 columns, use the approved 38-cell minimum for side-by-side pins, avoid tmux hooks and `select-layout`, and never target tmux pane indexes.
- Keep extension loading idempotent. Managed sessions still pass `--extension` so linked CLI usage works without `pi install`; when the package is also installed, the extension may load twice in one Pi process. Suppress duplicate registration, but clear active process guards on `session_shutdown` so later sessions can register. The extension heartbeat is the generic bridge for live Pi session state such as active theme and workflow stage. Compaction lifecycle handling belongs here: `session_before_compact` publishes transient running state, normal `session_compact` restores the pre-compaction state, and `agent_start` keeps a continuing turn running; `willRetry` clears the snapshot/watchdog while leaving the session running until `agent_start`. Serialized heartbeat writes prevent a stale watchdog restore from overwriting a newer lifecycle state. `Shift+F` marks the new process once with `PI_AGENT_HUB_FORK_COMPACT=1`; the Hub extension consumes and deletes that marker when it loads. Pi reports an initial CLI `pi --fork` as `session_start` reason `startup`, not `fork`, so this path must act on the marker rather than the event reason. Before compaction, it resets the native name to the primary repo basename and ignores inherited ticket/workflow entries until producers publish newer metadata. Fork-and-compact publishes a transient `fork-compact` heartbeat operation with `running`, `complete`, or `error` phases, passes one bounded handoff instruction to Pi, and the lifecycle caller reports success only after the exact child heartbeat reaches `complete`; timeout/error leaves the child available for inspection. It schedules compaction before awaited MCP startup work. The separate Hub-owned `theme-command.json` is a deliberately narrow one-time control bridge: parent extensions compare its timestamp/revision to process start, resolve the concrete global theme through Pi, apply a `Theme` object without rewriting settings, and heartbeat immediately; subagents and older commands are ignored. The workflow producer owns each ordered `WorkflowSnapshot.steps` definition, state-change timestamp, optional active-mode display, and optional `currentStepComplete` boolean. Hub validates the base workflow and each decoration independently but mirrors no step ids, short codes, labels, mode vocabulary, or legacy fallback; invalid decoration does not hide a valid base workflow. One pure positional marker rule serves project rows, board cards, and the action workspace: indexes before `activeIndex` are complete; the current index is complete only when `currentStepComplete === true`, otherwise active; later indexes are pending. Direct later-step invocation therefore checks earlier positions. This is a position cue rather than sequence enforcement or an execution audit. Completion does not change lane placement, and retained terminal snapshots remain visible across stale/shutdown state until a new workflow snapshot replaces them. Base workflow state may be retained in `registry.json`, but `SessionsController` merges a mode only into `RuntimeSession` from a fresh non-shutdown heartbeat with confirmed tmux presence, so modes never affect persistence or liveness.
- Managed-session lifecycle orchestration lives in `src/app/session-lifecycle.ts`; it owns add/start/stop/restart/fork, delete, subagent cleanup, and worktree finish/discard sequencing while reusing core adapters. Normal fork and Fork and compact share the same group-selection form; the compact variant adds only the one-shot startup behavior described above. `src/app/delete-session.ts` and `src/app/worktree-session.ts` remain explicit safety entry modules for delete and Git lifecycle flows and delegate to the central module; callers must keep using those entry paths. Normal delete stops tmux, removes any owned multi-repo workspace, removes the registry row, removes the heartbeat, and keeps Pi conversation/session files. Normal delete intentionally keeps hub-owned worktree directories; finish or discard worktree sessions after a clean-state preflight, then merge/remove or discard all session worktrees before removing registry rows and heartbeats. Multi-repo worktree finish/discard handles additional repos before the primary repo so partial failures keep the primary session cwd recoverable. Tmux, workspace, and Git work that determines a lifecycle mutation stays outside the lock and completes before the short registry update; after the registry commit, remove each session's heartbeat. `removeSessions(sessions, path, env)` filters only prepared IDs from the latest registry after tmux/workspace cleanup. Successful deletion removes only the prepared IDs from latest state, while partial worktree failure transforms the latest surviving parent after failed external work. Archive pruning is separate and dashboard-only after seven days: `src/app/controller.ts` removes expired archived registry rows plus heartbeat and owned multi-repo workspace state only after every row in the session/subagent cascade is confirmed missing from tmux. Refresh observes one tmux session-list snapshot for its initial registry and applies an observation only to a latest row with the same session ID, tmux target, and unchanged `updatedAt` version before projecting runtime fields or pruning. The TUI still pauses its local refresh loop around deletion/finish/discard for lifecycle ordering, while latest-state registry transformations independently preserve concurrent CLI, TUI, and external subagent writes.
- Groups are implicit flat labels on sessions, not separate records. Creating a session with a new group label creates the group; pressing `g` in the TUI moves the selected session to an existing or new group, while `G` renames the selected session's current group for all sessions in that group. Pressing `K`/`J` or Shift-Up/Shift-Down reorders the selected Active or Backlog session within its current group; Archived is globally chronological and cannot be manually reordered. Pressing `A`, `B`, or `U` archives, backlogs, or restores a parent session by updating optional `ManagedSession.bucket` / `bucketChangedAt` fields; these actions never stop tmux/Pi, and subagent rows inherit their top-level parent's effective lifecycle instead of moving directly. Archived shows the five newest parent cascades by default and exposes older cascades through an ephemeral disclosure target. In the project cockpit, Backlog is row metadata rather than a section header. `NEEDS YOU` is always expanded; HEALTH, ACTIVE, QUIET, and ARCHIVED are synthetic selectable tier targets with independent persisted collapse state. Archived also retains its separate older-cascade disclosure. `Enter` and double-click toggle the selected collapsible tier, while filtering reveals matching rows without mutating tier or tree disclosure state. The Archived header is a non-session target, so session actions remain inert; collapsing it repairs a hidden session selection to the header. Pressing `R` sends exact `/name <text>` to a live Pi session through the cursor-aware form used by in-session `Alt+R`; stopped/error rows require restart first. Normal name propagation updates the Hub cache. `N` remains manual recovery from the latest persisted Pi `session_info` name. In-session `Alt+R` keeps the explicit dashboard rename dialog because that flow temporarily leaves the managed session before switching back. Pressing `p` sends a one-line footer prompt to the selected live session through tmux paste without opening it. At 120+ columns, pressing `Enter` on a stopped or error row restarts it instead of attempting to attach. Below 120, `i` opens the exact selected action workspace without side effects; `Enter` remains the direct open/switch/restart action at every width. Pressing `r` opens restart choices: `r` resumes the selected saved Pi conversation, `n` clears the selected hub row's Pi session metadata and starts a new Pi conversation in the same tmux/session record, and `a` restarts all active non-subagent sessions while skipping Backlog and Archived. Do not add separate empty-group lifecycle unless the model changes.
- Active and Backlog source rows retain stable `default`-first group order. Inside each group, errors come first, then unacknowledged `waiting` rows newest-first, `starting`/`running`, acknowledged `waiting`/`idle` rows by activity, and stopped rows. The project cockpit then stable-partitions complete owner trees into its presentation tiers without changing that source order inside a tier; groups are muted row metadata rather than headings. `ManagedSession.order` is optional registry data, breaks exact priority/activity ties, and falls back to group-relative registry order; new/forked/group-moved sessions append to the target group within the current lifecycle section. `K`/`J` reorder only inside the selected row's current tie. `src/core/session-order.ts` owns this ordering while keeping Archived globally newest-first by archive time; every nonempty cockpit tier renders its heading. `src/core/session-tree.ts` builds on `src/core/session-order.ts` and owns both recursive subagent nesting and canonical ancestry lookup for navigation and render projections. Build one `createSessionTreeIndex()` per behaviorally meaningful row scope and reuse its cached trace; do not merge filtered, active, projected, lane-local, or raw-snapshot scopes. The index supplies ownership, depth, and linked-parent facts, while each projection applies its own unresolved-ancestry policy: archive lifecycle falls back to the row when a parent is missing; the project cockpit keeps missing-parent and cyclic terminal rows as standalone presentation owners; board lane and expansion ownership omit ownerless subagents; and archive lifecycle plus board grouping use the terminal cycle member. Titles never affect order, and stopped sessions remain in the group instead of rendering in a separate subsection.
- The selected-session action workspace uses only validated producer context, current runtime projections, workflow/status evidence, and catalog command descriptors. Question attention relabels the existing `open` command as **Answer**, makes it primary, and routes to the real Pi questionnaire through exact pin focus or normal attach; Hub does not mirror questionnaire options or accept answers. Hub does not capture, store, render, or search tmux pane tails or Pi conversation content. `src/app/refresh-loop.ts` refreshes observation state only; `SessionsController` has no preview snapshot or capture invalidation path.
- Keep rendering pure and testable in `src/tui/*`; ANSI styling must stay width-safe via theme helpers. One adaptive hierarchy derives card richness from row role, grouping, width, and height; card richness has no persisted or user-selectable setting. `S` toggles between the project attention cockpit and workflow-stage lanes. The project cockpit classifies complete owner trees from the full unfiltered fleet in strict order: explicit waiting/idle owner attention → `NEEDS YOU`, owner error → `HEALTH`, starting/running owner or descendant → `ACTIVE`, other non-archived owners → `QUIET`, while lifecycle-owned `ARCHIVED` stays separate. Descendants inherit placement without changing their own state, and filtering changes visibility only. Hidden explicit child requests are derived from the full-fleet owner projection, then request IDs present in the current visible projection are subtracted; only presentation owners and project tier headers receive the resulting counts, with no attention, placement, ordering, acknowledgement, or workflow promotion. Active project parent tails preserve a readable title and fit hidden requests, starting/running descendants, workflow, and activity age in that order; age drops first, full workflow compacts, descendant count drops, workflow drops, and hidden requests survive longest. Backlog uses its lifecycle label and optional group after any hidden-request badge. Archived excludes descendant/workflow signals but may pair a hidden-request badge with its age. Lifecycle still controls row/card richness and glyph treatment. In stage grouping, lane headers and producer workflow-tree projection apply independently of project card richness. Dashboard rendering must be safe at any pane size: `SessionsView.render()` owns the below-40-col narrow notice, `renderSessions()` bounds output to terminal height, and mouse hit maps must describe only visible rows. The stage-grouping projection reuses `RenderSection`: it chooses one deterministic producer pipeline from filtered Active parents, keeps compatible trees in producer lane order, then appends synthetic `OTHER ACTIVE` for every workflowless or incompatible Active parent tree. Backlog/Archived stay footer-only. Every section nests rows under the top-level parent's existing group; headings count parents only and no row repeats its group. Subagent descendants are omitted by default through separate ephemeral project/stage `SessionsView` expansion sets. `←`/`→` collapses or expands the selected top-level tree; `Shift+←`/`Shift+→` applies to every tree in the current grouping; `Space` remains a stage-group selected-tree toggle. `▸`/`▾` reflects projection state, collapsing a selected descendant repairs selection to its parent, and an active filter reveals matching tree context without mutating either set. Only visible children receive row targets. Optional producer modes substitute active-step display without entering pipeline identity or lane selection; stopped rows suppress mode decoration while retaining their base lane.
